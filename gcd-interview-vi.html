0. Queue vs Thread — hình dung nền

Hầu hết hiểu lầm về GCD đều bắt nguồn từ chỗ gộp hai khái niệm này làm một. Gỡ được phần này thì các câu sau dễ hẳn.

● Queue và Thread khác nhau thế nào?

Câu chốt: queue không chạy code. Queue chỉ giữ code. Thread mới là thứ chạy.

ThreadQueue
Là gìThứ thực sự chạy codeDanh sách công việc chờ được chạy
Ai tạoHệ điều hànhBạn — DispatchQueue(label:)
Chi phíĐắt — mỗi cái ~512KB stackRẻ — chỉ là một object nhỏ
Số lượng hợp lýÍt (vài chục là quá nhiều)Thoải mái, hàng nghìn cũng được
Chạy code khôngCóKhông

Ẩn dụ nhà bếp

Queue = tập phiếu order dán trên kẹp. Thread = đầu bếp. GCD = bếp trưởng phân công phiếu nào cho ai.

QUEUE A  [phiếu][phiếu][phiếu]  ─┐
                                 ├─→  GCD phân công  ─→  [đầu bếp 1]
QUEUE B  [phiếu][phiếu]         ─┤                       [đầu bếp 2]
                                 │                       [đầu bếp 3]
QUEUE C  [phiếu]                ─┘                       [đầu bếp 4]

Phiếu order tự nó không nấu được gì. 50 kẹp phiếu nhưng chỉ 4 đầu bếp là hoàn toàn bình thường — đó là lý do tạo nhiều queue thì rẻ mà tạo nhiều thread thì đắt.

Vì sao tách hai khái niệm lại hay

Với Thread bạn phải nghĩ "cần bao nhiêu thread, tạo lúc nào, huỷ lúc nào" — câu hỏi về tài nguyên hệ thống. Với GCD bạn chỉ nghĩ "những việc này có cần tuần tự không" — câu hỏi về logic nghiệp vụ. Phần ánh xạ queue → thread để GCD lo.

● Serial queue có thread riêng của nó không?

Không. Đây là hiểu lầm phổ biến nhất. "Serial" chỉ có nghĩa mỗi lúc chỉ một việc trong queue này được chạy. Việc đó chạy trên thread nào thì không cố định.

let q = DispatchQueue(label: "myQueue")   // serial

q.async { print("việc 1 —", Thread.current) }
q.async { print("việc 2 —", Thread.current) }
q.async { print("việc 3 —", Thread.current) }

việc 1 — NSThread 0x600001  number = 5
việc 2 — NSThread 0x600002  number = 7   ← thread khác!
việc 3 — NSThread 0x600001  number = 5   ← lại quay về

Ba việc chạy tuần tự (đảm bảo) nhưng trên ba thread khác nhau (không đảm bảo gì). GCD mượn thread nào rảnh trong pool thì dùng.

Serial đảm bảo thứ tự, không đảm bảo thread

Hệ quả thực tế: nếu code cũ của bạn dựa vào thread-local storage, migrate từ Thread sang serial queue sẽ hỏng — serial queue không giữ bạn ở cùng một thread.

● Main queue và main thread — quan hệ thế nào?

Đây là cặp duy nhất bị ràng buộc 1:1, và cũng là lý do hai khái niệm hay bị nhập làm một.

  • Main thread — một thread OS thật, tạo ngay khi app khởi động, chạy run loop, chỉ nó được chạm UIKit, sống tới khi app tắt.
  • Main queue — một serial queue đặc biệt: mọi work item trong nó luôn luôn được main thread chạy, không bao giờ thread khác.
┌──────────────┐          ┌──────────────┐
│  MAIN QUEUE  │ ──1:1──→ │ MAIN THREAD  │   gắn cố định
└──────────────┘          └──────────────┘

┌──────────────┐          ┌──────────────┐
│ queue của bạn│ ── ? ──→ │ thread pool  │   mượn thread nào cũng được
└──────────────┘          └──────────────┘

Vì ràng buộc này nên trong thực tế nói "đưa về main queue" và "chạy trên main thread" gần như tương đương. Nhưng về khái niệm vẫn là hai thứ: một cái là danh sách, một cái là người làm.

Nói thế nào

"Em nghĩ thread là thứ thực sự chạy code, còn queue chỉ là danh sách công việc đang chờ. Queue tự nó không làm gì — GCD lấy việc từ queue rồi giao cho một thread trong pool.

Nên serial queue không có nghĩa là nó có thread riêng. Nó chỉ đảm bảo mỗi lúc một việc, còn việc đó chạy trên thread nào thì GCD quyết. Ngoại lệ duy nhất là main queue — mọi việc trong nó luôn do main thread chạy, vì UIKit yêu cầu vậy.

Ý nghĩa của việc tách hai khái niệm là mình chỉ cần nghĩ về công việc và thứ tự, không phải nghĩ về tài nguyên hệ thống. Nên tạo hai chục queue thì bình thường, còn tạo hai chục thread thì rất tệ."

1. Nhóm 1 — Nền tảng

Gần như chắc chắn được hỏi ở mọi vòng phỏng vấn iOS.

● GCD là gì? Khác gì Thread và OperationQueue?

Nói thế nào

"GCD là công cụ chạy code bất đồng bộ của Apple. Điểm chính là mình không quản lý thread nữa — chỉ đưa việc vào hàng đợi, hệ thống tự lo chạy trên thread nào.

So với Thread, khác biệt là ai chịu trách nhiệm vòng đời. Tự tạo thread thì vừa tốn bộ nhớ vừa dễ tạo quá nhiều.

OperationQueue thì xây trên nền GCD nhưng ở tầng cao hơn — cho phép huỷ, đặt phụ thuộc giữa các tác vụ, và giới hạn số việc song song. Cần ba thứ đó thì em dùng nó, còn việc đơn giản thì GCD gọn hơn."

// Thread — tự quản mọi thứ, hiếm khi dùng trực tiếp
let t = Thread { print("chạy trên thread riêng") }
t.start()

// GCD — chỉ nghĩ về công việc
DispatchQueue.global(qos: .userInitiated).async {
    let image = processImage()
    DispatchQueue.main.async { imageView.image = image }
}

// OperationQueue — khi cần phụ thuộc, huỷ, giới hạn
let queue = OperationQueue()
queue.maxConcurrentOperationCount = 3

let download = BlockOperation { print("tải ảnh") }
let resize   = BlockOperation { print("resize") }
resize.addDependency(download)          // resize chờ download xong

queue.addOperations([download, resize], waitUntilFinished: false)
queue.cancelAllOperations()             // GCD không làm được điều này

Hỏi vặn thường gặp: "ví dụ dependency?" → Tải ảnh xong mới resize, resize xong mới upload.

● Serial queue và Concurrent queue khác nhau thế nào?

Nói thế nào

"Serial queue là hàng đợi chỉ có một người làm — việc nào vào trước xong trước, việc sau đợi việc trước kết thúc hẳn. Nên thứ tự luôn được đảm bảo.

Concurrent queue thì nhiều việc được bắt đầu cùng lúc. Em nhấn mạnh 'bắt đầu' vì thứ tự bắt đầu vẫn theo hàng đợi, nhưng thứ tự kết thúc thì không đoán được.

Em dùng serial khi cần bảo vệ dữ liệu dùng chung, dùng concurrent cho những việc độc lập như tải mười cái ảnh.

À và một chỗ nhiều người nhầm: DispatchQueue(label:) tạo ra là serial. Muốn concurrent phải truyền thêm attributes."

// SERIAL — mặc định khi chỉ truyền label
let serial = DispatchQueue(label: "com.app.serial")

serial.async { print("A bắt đầu"); sleep(2); print("A xong") }
serial.async { print("B bắt đầu"); print("B xong") }
// LUÔN LUÔN: A bắt đầu → A xong → B bắt đầu → B xong

// CONCURRENT — phải khai báo rõ
let concurrent = DispatchQueue(label: "com.app.concurrent",
                               attributes: .concurrent)

concurrent.async { print("A bắt đầu"); sleep(2); print("A xong") }
concurrent.async { print("B bắt đầu"); print("B xong") }
// A bắt đầu → B bắt đầu → B xong → A xong
// B bắt đầu sau nhưng xong trước

● sync và async khác nhau ra sao?

Nói thế nào

"Sync và async nói về thread đang gọi, không nói về queue đích.

async là đưa việc vào queue rồi đi tiếp ngay. sync là đưa việc vào queue rồi đứng đợi tới khi xong mới chạy dòng tiếp.

Chỗ nhiều người nhầm là tưởng async đồng nghĩa 'chạy song song'. Không phải — nếu em async mười việc lên serial queue thì chúng vẫn chạy lần lượt. async chỉ có nghĩa thread gọi không phải chờ. Muốn song song thì queue phải là concurrent."

// ASYNC — không chờ
print("1")
DispatchQueue.global().async { print("2") }
print("3")
// Output: 1 → 3 → 2

// SYNC — chờ xong mới đi tiếp
print("1")
DispatchQueue.global().sync { print("2") }
print("3")
// Output: 1 → 2 → 3  (luôn luôn)

// Chứng minh async ≠ song song
let serial = DispatchQueue(label: "serial")
for i in 1...3 { serial.async { print(i) } }
// async nhưng vẫn ra 1 → 2 → 3

Hỏi vặn: "vậy khi nào dùng sync?"

"Em ít dùng vì nó block thread và dễ deadlock. Trường hợp chính đáng gần như chỉ còn là đọc dữ liệu từ queue bảo vệ, vì cần giá trị trả về ngay."

final class Counter {
    private var value = 0
    private let queue = DispatchQueue(label: "counter")

    func increment() {
        queue.async { self.value += 1 }      // ghi: không cần chờ
    }
    var current: Int {
        queue.sync { value }                 // đọc: buộc phải chờ để có giá trị
    }
}

● Main queue là serial hay concurrent? Vì sao?

Nói thế nào

"Serial ạ. Và em nghĩ nó bắt buộc phải như vậy.

Vì toàn bộ UIKit không thread-safe. Nếu main queue là concurrent thì hai đoạn code có thể cùng lúc sửa một view — một bên đang tính layout, một bên đổi frame — kết quả không đoán được, hoặc crash, hoặc giao diện vẽ sai.

Ngoài ra màn hình chỉ vẽ lại theo từng nhịp, khoảng 16 mili giây một lần với màn 60Hz. Mọi thay đổi UI được gom lại và áp dụng cùng một lượt — mô hình một luồng duy nhất hợp lý hơn."

// Main queue chạy tuần tự — thứ tự này luôn đúng
DispatchQueue.main.async { print("1") }
DispatchQueue.main.async { print("2") }
DispatchQueue.main.async { print("3") }
// Output: 1 → 2 → 3

// Pattern chuẩn: việc nặng ở background, chạm UI ở main
func loadAvatar() {
    DispatchQueue.global(qos: .userInitiated).async {
        let data  = try? Data(contentsOf: self.url)
        let image = data.flatMap(UIImage.init)

        DispatchQueue.main.async {
            self.imageView.image = image
        }
    }
}

● QoS là gì? Kể các mức và khi nào dùng mức nào

Đừng đọc thuộc năm mức. Nói theo tiêu chí chọn.

Nói thế nào

"Em nghĩ về nó theo câu hỏi: user có đang đợi cái này không, và đợi bao lâu thì thấy khó chịu?

User Interactive — user đang nhìn thẳng vào nó, phải xong trong tích tắc. Animation, xử lý cử chỉ vuốt.
User Initiated — user vừa bấm và đang chờ kết quả, chấp nhận vài giây. Mở màn hình chi tiết.
Utility — có thanh tiến trình, user biết là lâu. Tải file, import dữ liệu.
Background — user không biết nó đang chạy. Đồng bộ, dọn cache, gửi analytics.

Điều em để ý là QoS không chỉ ảnh hưởng ưu tiên CPU mà cả ưu tiên I/O và mức tiêu pin. Việc ở background sẽ bị hệ thống hoãn khi máy sắp hết pin hoặc đang tiết kiệm năng lượng."

// User vừa bấm nút, đang chờ kết quả
DispatchQueue.global(qos: .userInitiated).async {
    let results = database.search(keyword)
    DispatchQueue.main.async { self.tableView.reloadData() }
}

// Có progress bar, user biết là lâu
DispatchQueue.global(qos: .utility).async {
    exportVideo(progress: { updateProgressBar($0) })
}

// User không biết nó tồn tại
DispatchQueue.global(qos: .background).async {
    cleanupOldCacheFiles()
    analytics.flush()
}

// Queue tự tạo cũng gán được QoS
let importQueue = DispatchQueue(label: "com.app.import", qos: .utility)

Hỏi vặn: "nếu task QoS thấp bị task QoS cao chờ thì sao?" → Hệ thống tạm nâng mức ưu tiên của task thấp lên để nó xong sớm mà nhả tài nguyên. Nếu không thì task cao bị kẹt vì chờ một thứ hiếm khi được chạy — cái đó gọi là priority inversion.

● Vì sao phải update UI trên main thread?

Nói thế nào

"Có ba lý do.

Thứ nhất, UIKit không thread-safe — hai luồng cùng sửa một view dẫn tới trạng thái hỏng, crash, hoặc giao diện vẽ sai, mà lỗi kiểu này rất khó tái hiện.

Thứ hai, vòng lặp vẽ màn hình gắn với run loop của main thread. Đổi thuộc tính view từ thread khác có thể rơi vào giữa chu kỳ vẽ và không được áp dụng đúng lúc.

Thứ ba, sự kiện chạm, vuốt, bàn phím đều được phân phối trên main thread. Đọc và ghi trạng thái UI ở cùng một chỗ thì đơn giản hơn nhiều so với đồng bộ giữa nhiều thread."

// ❌ SAI — chạm UI từ background
URLSession.shared.dataTask(with: url) { data, _, _ in
    self.imageView.image = UIImage(data: data!)
    self.activityIndicator.stopAnimating()
}.resume()

// ✅ ĐÚNG
URLSession.shared.dataTask(with: url) { data, _, _ in
    let image = data.flatMap(UIImage.init)          // decode: để ở background
    DispatchQueue.main.async {
        self.imageView.image = image                // chạm UI: về main
        self.activityIndicator.stopAnimating()
    }
}.resume()

Helper an toàn — tránh nhảy queue thừa và tránh crash:

func onMain(_ work: @escaping () -> Void) {
    if Thread.isMainThread {
        work()                                  // đã ở main, gọi thẳng
    } else {
        DispatchQueue.main.async(execute: work)
    }
}

Không dùng DispatchQueue.main.sync cho việc này, vì nếu đang ở main thread rồi thì nó crash — xem phần Deadlock & circular wait.

Hỏi vặn: "làm sao phát hiện mình lỡ update UI sai thread?" → Xcode có Main Thread Checker bật sẵn khi debug, nó cảnh báo ngay tại dòng gọi sai.

Bốn câu tự nêu ra để ghi điểm ở nhóm 1

  • DispatchQueue(label:) mặc định là serial
  • async không đồng nghĩa với chạy song song
  • sync block thread gọi, không liên quan loại queue đích
  • DispatchQueue.main.sync từ main thread crash ngay

2. Nhóm 2 — Thực hành

Hay gặp ở vòng mid-level. Nhóm này kiểm tra bạn đã thật sự dùng GCD trong dự án hay chưa.

● DispatchGroup dùng để làm gì?

Nói thế nào

"Em dùng khi có nhiều việc chạy song song nhưng cần biết khi nào tất cả xong để làm bước tiếp theo.

Tình huống kinh điển là màn hình trang chủ cần ba nguồn dữ liệu — thông tin người dùng, danh sách sản phẩm, banner khuyến mãi. Ba API độc lập nên gọi song song cho nhanh, nhưng chỉ khi cả ba về đủ em mới ẩn loading.

Nếu không có DispatchGroup thì em phải tự đếm biến, mà biến đó lại bị nhiều thread chạm vào nên phải tự lo đồng bộ. Group xử lý sẵn phần đó."

func loadHomeScreen() {
    let group = DispatchGroup()
    var profile: Profile?
    var products: [Product] = []
    var banners: [Banner] = []

    group.enter()
    api.fetchProfile { profile = try? $0.get(); group.leave() }

    group.enter()
    api.fetchProducts { products = (try? $0.get()) ?? []; group.leave() }

    group.enter()
    api.fetchBanners { banners = (try? $0.get()) ?? []; group.leave() }

    // Chạy khi cả ba đã leave đủ
    group.notify(queue: .main) {
        self.render(profile: profile, products: products, banners: banners)
        self.hideLoading()
    }
}

notify khác wait thế nào

group.notify(queue: .main) { }   // ✅ không block, chạy callback khi xong
group.wait()                     // ⚠️ block thread hiện tại
group.wait(timeout: .now() + 5)  // block nhưng có hạn, trả .timedOut

"Em gần như luôn dùng notify. wait block thread, lỡ gọi trên main thread thì đơ app."

● enter/leave khác gì group.async?

Câu chốt: group.async báo "xong" sai thời điểm khi việc bên trong có callback.

DispatchGroup thực ra chỉ là một bộ đếm

group = bộ đếm, khởi tạo = 0

enter()  → đếm + 1
leave()  → đếm - 1
notify   → bắn khi đếm về 0

Và group.async chỉ là đường tắt:

group.async { work() }

// tương đương y hệt với:
group.enter()
queue.async {
    work()
    group.leave()     // ← tự động gọi khi CLOSURE KẾT THÚC
}

Mấu chốt ở dòng cuối: group.async tự leave() tại thời điểm closure chạy hết dòng cuối. Nó không biết gì hơn thế.

Vì sao hỏng với công việc bất đồng bộ

// ❌ SAI
group.async {
    URLSession.shared.dataTask(with: url) { data, _, _ in
        results.append(data)          // chạy SAU khi notify đã bắn
    }.resume()
}                                     // closure kết thúc ngay tại đây
group.notify(queue: .main) {
    print(results.count)              // in ra 0
}

0.001s: closure kết thúc → leave() → đếm về 0 → notify BẮN  ✗
2.0s:   network trả về   → results.append(data)  ← quá muộn
// ✅ ĐÚNG — tự chọn thời điểm báo xong
group.enter()
URLSession.shared.dataTask(with: url) { data, _, _ in
    results.append(data)
    group.leave()                     // đúng lúc dữ liệu thật sự về
}.resume()

Cả hai cách đều song song y hệt nhau

enter/leave không làm gì tuần tự. Chúng chỉ là hai lời khai báo "tôi bắt đầu" và "tôi xong rồi". Khác biệt duy nhất so với group.async là mốc thời gian được tính là hoàn thành.

● DispatchSemaphore dùng khi nào?

Nói thế nào

"Em dùng chủ yếu để giới hạn số tác vụ chạy đồng thời.

Ví dụ màn hình upload nhiều ảnh. Nếu user chọn 200 ảnh mà bắn hết cùng lúc thì vừa nghẽn mạng, vừa tốn RAM, server cũng có thể chặn. Em dùng semaphore giá trị 4 để mỗi lúc chỉ 4 upload chạy song song.

Cơ chế thì nó là một bộ đếm: wait() giảm 1, nếu xuống dưới 0 thì thread bị chặn; signal() tăng 1 và giải phóng một thread đang chờ."

func uploadAll(_ files: [File]) {
    let semaphore = DispatchSemaphore(value: 4)   // tối đa 4 cùng lúc
    let group = DispatchGroup()

    DispatchQueue.global(qos: .utility).async {
        for file in files {
            semaphore.wait()                      // chờ tới khi có chỗ trống
            group.enter()
            api.upload(file) { _ in
                semaphore.signal()                // trả chỗ
                group.leave()
            }
        }
        group.notify(queue: .main) { print("upload xong hết") }
    }
}

Ba use case hợp lệ

  1. Giới hạn số tác vụ đồng thời — chính đáng nhất, dùng nhiều nhất.
  2. Mutex (value: 1) — nhưng NSLock hoặc os_unfair_lock nhanh hơn và rõ nghĩa hơn; os_unfair_lock còn chống priority inversion.
  3. Biến async → sync ở biên hệ thống — khi một API bắt buộc trả kết quả đồng bộ (URLProtocol custom, extension cũ).

● Viết một collection thread-safe bằng GCD

Câu ra nhiều nhất trong cả nhóm GCD — nó gộp serial/concurrent, sync/async và barrier vào một bài. Trả lời theo ba bước tăng dần để thể hiện chiều sâu.

Bước 1 — serial queue

"Cách cơ bản nhất là bọc mọi truy cập trong một serial queue. Vì serial chỉ cho một việc chạy tại một thời điểm nên không bao giờ có hai luồng cùng chạm vào dữ liệu."

final class SafeCache {
    private var storage: [String: Data] = [:]
    private let queue = DispatchQueue(label: "com.app.cache")

    func set(_ value: Data, for key: String) {
        queue.async { self.storage[key] = value }        // ghi: không cần chờ
    }
    func get(_ key: String) -> Data? {
        queue.sync { storage[key] }                      // đọc: cần giá trị
    }
}

Bước 2 — readers-writers bằng barrier

"Cách trên chưa tối ưu: đọc vốn an toàn khi làm song song, nhiều luồng cùng đọc không gây xung đột. Serial queue lại bắt chúng xếp hàng không cần thiết. Nên em dùng concurrent queue cho đọc song song, còn khi ghi thì gắn cờ .barrier."

final class SafeCache {
    private var storage: [String: Data] = [:]
    private let queue = DispatchQueue(label: "com.app.cache",
                                      attributes: .concurrent)

    func get(_ key: String) -> Data? {
        queue.sync { storage[key] }                       // đọc song song
    }
    func set(_ value: Data, for key: String) {
        queue.async(flags: .barrier) { self.storage[key] = value }
    }
    func remove(_ key: String) {
        queue.async(flags: .barrier) { self.storage.removeValue(forKey: key) }
    }
    var count: Int { queue.sync { storage.count } }
}

"Mỗi lời gọi thì an toàn, nhưng ghép hai lời gọi lại thì giữa chúng có khe hở."

● Barrier là gì? Giải thích readers-writers

Nói thế nào

"Ý tưởng xuất phát từ một quan sát: đọc dữ liệu song song thì an toàn, ghi thì không. Nhiều luồng cùng đọc một dictionary không gây hỏng gì, nhưng chỉ cần một luồng ghi trong lúc luồng khác đọc là dữ liệu có thể sai hoặc crash.

Nên em dùng concurrent queue để đọc chạy song song, còn khi ghi thì gắn cờ .barrier. Barrier bảo queue: đợi mọi việc đang chạy xong hết, cho block này chạy một mình, xong mới cho các việc sau tiếp tục."

let queue = DispatchQueue(label: "cache", attributes: .concurrent)

queue.sync { storage[key] }                            // đọc — song song
queue.async(flags: .barrier) { storage[key] = value }  // ghi — độc quyền

Điều kiện bắt buộc — nên chủ động nói

Barrier chỉ có tác dụng trên queue tự tạo với attributes: .concurrent. Trên DispatchQueue.global() thì cờ barrier bị bỏ qua, vì global queue được chia sẻ toàn hệ thống, không thể để một app chặn nó. Trên serial queue thì barrier vô nghĩa vì mọi thứ đã tuần tự sẵn.

Đây là lỗi rất khó phát hiện: DispatchQueue.global().async(flags: .barrier) trông có vẻ đúng nhưng dữ liệu vẫn không an toàn.

"Vì đọc cần giá trị trả về nên buộc phải chờ. Ghi thì không trả về gì nên không cần chờ. Tính độc quyền là do .barrier đảm bảo, không liên quan tới sync hay async."

● Thread explosion là gì? Nguyên nhân và cách tránh

Nói thế nào

"Là khi GCD sinh ra quá nhiều thread, tới mức CPU tốn thời gian chuyển qua lại giữa chúng nhiều hơn là làm việc thật.

Nguyên nhân là mình đưa vào global queue những việc chặn thread — chờ semaphore, đọc file đồng bộ, hoặc chờ lock. Thread đó không làm gì nhưng cũng không thể bỏ việc xuống để nhận việc khác. Hệ thống thấy còn việc tồn mà không ai làm nên bơm thêm thread.

Mỗi thread tốn khoảng 500KB bộ nhớ. GCD có trần 64 thread cho mỗi mức QoS — chạm trần mà vẫn còn việc chờ thì app đơ hẳn."

Cơ chế chính xác hơn

Không phải GCD "thấy không thread nào rảnh". Kernel workqueue duy trì một mục tiêu số thread đang chạy được (thường = số core). Khi một thread chuyển sang trạng thái blocked, kernel thấy số thread runnable tụt xuống dưới mục tiêu; nếu queue còn việc, nó bơm thêm một thread để lấp chỗ.

Mấu chốt: kernel không phân biệt được thread đang tính toán nặng với thread đang ngồi chờ vô ích. Cả hai đều "chiếm chỗ", nên nó cứ bơm thêm.

Lưu ý: chỉ global concurrent queue (và queue có attributes: .concurrent) mới overcommit như vậy. Serial queue của bạn không bao giờ sinh thêm thread — nó chỉ đơn giản là tắc.

// ❌ Sinh rất nhiều thread
for i in 0..<100 {
    DispatchQueue.global().async {
        let sem = DispatchSemaphore(value: 0)
        api.fetch(i) { _ in sem.signal() }
        sem.wait()                    // chặn thread
    }
}

// ✅ Giới hạn số việc song song
let limiter = DispatchSemaphore(value: 4)
let queue = DispatchQueue(label: "work", attributes: .concurrent)
for i in 0..<100 {
    queue.async {
        limiter.wait()
        api.fetch(i) { _ in limiter.signal() }
    }
}

Cooperative pool của Swift Concurrency

Swift Concurrency chạy trên thread pool cố định = số CPU core (iOS device thường 4–6), không bao giờ sinh thêm. Nó làm được vì await không block:

GCD blocking:                      Swift await:

[thread] ──chờ──── ...             [thread] ──suspend──→ nhận task khác
  stack bị treo                      state lưu heap, thread tự do
  kernel bơm thread mới              resume sau bởi thread bất kỳ

Tại await, trạng thái local được lưu vào một frame trên heap và thread được trả về pool ngay. Runtime biết task đang chờ nên không cần bơm thread. GCD chờ ở tầng OS (kernel mù thông tin), Swift chờ ở tầng runtime (biết rõ ngữ cảnh).

Swift Concurrency không tự động miễn nhiễm

Nó thay thread explosion bằng thread starvation. Nếu bạn vẫn block bên trong hàm async (semaphore, sleep, sync I/O, vòng lặp CPU không yield), pool cạn kiệt còn nhanh hơn — vì nó cố định ở ~6 thread chứ không nở ra như GCD.

Ba thứ hay bị bỏ sót: Data(contentsOf:) với file lớn, NSLock giữ qua nhiều dòng tính toán, và vòng while xử lý ảnh không có await Task.yield().

● Priority inversion là gì? GCD xử lý thế nào?

Nói thế nào

"Là khi một tác vụ ưu tiên cao bị kẹt vì phải chờ một tác vụ ưu tiên thấp — mà tác vụ thấp thì hiếm khi được CPU cho chạy. Kết quả là việc quan trọng lại chậm nhất.

Ví dụ một tác vụ nền đang giữ lock để ghi cache. Main thread cần đọc cache nên phải chờ lock. Nhưng tác vụ nền ở mức background nên hệ thống hiếm khi lên lịch cho nó — main thread chờ dài, UI giật."

let lowQueue  = DispatchQueue(label: "low",  qos: .background)
let highQueue = DispatchQueue(label: "high", qos: .userInteractive)

lowQueue.async { heavyWork() }

highQueue.sync {
    lowQueue.sync { readData() }     // ⚠️ ưu tiên cao chờ ưu tiên thấp
}

"GCD có cơ chế priority donation — khi phát hiện queue ưu tiên cao đang chờ queue ưu tiên thấp, nó tạm nâng mức ưu tiên của queue thấp lên cho xong sớm mà nhả tài nguyên. os_unfair_lock cũng hỗ trợ điều này.

Nhưng DispatchSemaphore thì không — nó chỉ là bộ đếm, hệ thống không biết ai đang chờ ai. Nên dùng semaphore giữa hai mức QoS khác nhau thì priority inversion không được xử lý."

Cách phát hiện: Xcode có Thread Performance Checker, bật lên nó cảnh báo khi thấy priority inversion lúc chạy debug.

● DispatchQueue(label:) mặc định là serial hay concurrent?

Serial. Rất nhiều người trả lời sai câu này.

● Target queue là gì? Queue hierarchy hoạt động ra sao?

Nói thế nào

"Mọi queue mình tạo ra thực ra không tự chạy code. Nó trỏ tới một queue khác, và cuối cùng chuỗi đó dẫn tới một trong các global queue — nơi thật sự có thread chạy.

Mình có thể tự đặt queue nào trỏ tới queue nào bằng tham số target. Ứng dụng chính là gom nhiều queue lại dưới một serial queue chung, để tất cả tự động tuần tự với nhau mà vẫn tách biệt về mặt code."

let productQueue = DispatchQueue(label: "com.app.db.product", target: rootQueue)
let orderQueue   = DispatchQueue(label: "com.app.db.order",   target: rootQueue)

"Ba queue này về mặt code là ba module riêng, nhưng vì cùng trỏ về một serial queue nên chúng không bao giờ chạy song song với nhau — đúng thứ mình cần khi cả ba cùng truy cập một database không thread-safe.

Lợi ích nữa là giảm số thread. Nếu để ba queue độc lập, mỗi cái có thể chiếm một thread; gom lại thì cả ba dùng chung một, tránh được thread explosion."

Cảnh báo nên nêu kèm

userQueue.sync {
    productQueue.sync { }        // ⚠️ deadlock — thực chất cùng một serial queue gốc
}

● DispatchQueue.global() khác gì queue tự tạo?

Nói thế nào

"Global queue là queue dùng chung toàn hệ thống, mỗi mức QoS có một cái. Em không sở hữu nó, và mọi framework trong app cũng đang dùng chung.

Hệ quả là: một, em không đặt được .barrier trên đó. Hai, nếu em chặn thread ở đó thì ảnh hưởng tới cả phần khác của app. Ba, trong Instruments em không phân biệt được việc của mình với việc của thư viện khác vì nhãn giống nhau hết.

Nên em dùng global queue cho việc dùng một lần, ngắn gọn. Còn một module có trạng thái cần bảo vệ thì em luôn tạo queue riêng có label rõ ràng."

// Việc dùng một lần, ngắn
DispatchQueue.global(qos: .userInitiated).async {
    let result = compute()
    DispatchQueue.main.async { self.label.text = result }
}

// Module có trạng thái — queue riêng
final class ImageCache {
    private let queue = DispatchQueue(label: "com.app.imagecache",
                                      attributes: .concurrent)
}

● Khi nào chọn OperationQueue thay vì GCD?

Nói thế nào

"Em chọn OperationQueue khi cần một trong bốn thứ:

Thứ nhất là huỷ. GCD gần như không huỷ được sau khi đã submit, còn Operation có cancel() sẵn và huỷ được cả hàng đợi.

Thứ hai là phụ thuộc giữa các tác vụ. Tải ảnh xong mới resize, resize xong mới upload — với GCD phải lồng callback hoặc dùng group, còn ở đây chỉ cần khai báo.

Thứ ba là giới hạn số việc song song — một dòng maxConcurrentOperationCount, không cần semaphore.

Thứ tư là khi tác vụ có trạng thái riêng cần theo dõi, hoặc cần đóng gói thành class tái dùng được."

let queue = OperationQueue()
queue.maxConcurrentOperationCount = 3
queue.qualityOfService = .userInitiated

let download = BlockOperation { self.data = downloadFile() }
let process  = BlockOperation { self.result = process(self.data) }
let save     = BlockOperation { save(self.result) }

process.addDependency(download)
save.addDependency(process)

queue.addOperations([download, process, save], waitUntilFinished: false)
queue.cancelAllOperations()

final class DownloadOperation: Operation {
    let url: URL
    init(url: URL) { self.url = url }

    override func main() {
        guard !isCancelled else { return }
        let data = try? Data(contentsOf: url)
        guard !isCancelled else { return }     // kiểm tra lại sau việc nặng
        save(data)
    }
}

"Ngược lại, với việc đơn giản kiểu chạy background rồi về main thì GCD gọn hơn hẳn — OperationQueue có overhead lớn hơn vì mỗi operation là một object với KVO.

Còn nếu là dự án mới thì em nghiêng về async/await với TaskGroup, vì nó có sẵn cả huỷ lẫn phụ thuộc mà code đọc dễ hơn nhiều."

Bốn điểm chốt của nhóm 3

  • Barrier chỉ hoạt động trên concurrent queue tự tạo — global queue bỏ qua cờ này
  • Priority donation có với lock và queue, không có với semaphore
  • Target queue gom nhiều queue thành một luồng chung — vừa an toàn vừa giảm thread
  • OperationQueue thắng ở huỷ và phụ thuộc, thua ở độ gọn

4. Deadlock & circular wait — trace từng dòng

Phần này tách riêng vì nó là chỗ khó hình dung nhất, và cũng là câu interviewer hay đào sâu nhất.

● Deadlock là gì? Có crash app luôn không?

Deadlock là tình huống hai hoặc nhiều luồng chờ nhau vĩnh viễn, không luồng nào tiến được.

// Thread A                    // Thread B
lockA.lock()                   lockB.lock()
lockB.lock()  // chờ B nhả     lockA.lock()  // chờ A nhả

Bốn điều kiện Coffman

Deadlock chỉ xảy ra khi cả bốn cùng đúng — phá vỡ một cái là hết:

  1. Mutual exclusion — tài nguyên chỉ một luồng giữ được tại một thời điểm
  2. Hold and wait — đang giữ cái này, lại đi chờ cái khác
  3. No preemption — không ai cướp được tài nguyên từ luồng đang giữ
  4. Circular wait — vòng chờ khép kín A→B→A

Cách phá phổ biến nhất trong thực tế là phá điều kiện 4: quy định thứ tự cố định khi lấy nhiều lock.

Có crash không?

Về bản chất: không. Deadlock không phải lỗi bộ nhớ, không signal nào bị raise — luồng chỉ ngồi chờ. Nhưng hậu quả rất khác nhau tuỳ vị trí:

Tình huốngKết quả
DispatchQueue.main.sync gọi từ main threadCrash ngay — libdispatch phát hiện và trap
queue.sync lên chính serial queue đang chạyCrash ngay — cùng cơ chế
Main thread bị block lúc launch / chuyển stateApp bị kill — watchdog, 0x8badf00d
Main thread bị block khi app đang chạy bình thườngĐơ UI, không crash — user phải force-quit
Background thread deadlockIm lặng hoàn toàn — 1 feature chết, không log
Cooperative pool cạn kiệtMọi async đứng hình, UI vẫn vẽ nhưng không load được gì

Nuance hay bị nhầm về watchdog

0x8badf00d chỉ fire khi main thread không phản hồi quá lâu trong lúc chuyển trạng thái vòng đời: launch (~20s), resume, suspend, terminate. Nếu app đang ở foreground và không ở điểm chuyển trạng thái thì iOS không nhất thiết kill — app chỉ đơ, spinner xoay mãi. Đó là lý do hang khó phát hiện hơn crash.

Cách chẩn đoán

Khi app đơ, bấm Pause (⏸) trong Xcode rồi xem Debug Navigator. Deadlock hiện ra ngay: hai thread cùng dừng ở __psynch_mutexwait hoặc _dispatch_sema4_wait. Trong lldb dùng bt all.

  • Main Thread Checker — bắt UIKit call sai thread
  • Thread Performance Checker — cảnh báo priority inversion và thread block quá lâu
  • Instruments → System Trace — nhìn thread nào đang blocked và bởi gì
  • Thread Sanitizer bắt data race, không bắt deadlock — đừng nhầm

Nói thế nào

"Deadlock tự nó không crash — nó treo. Nhưng nếu treo trên main thread thì watchdog sẽ kill app với 0x8badf00d, còn DispatchQueue.main.sync từ main thread thì libdispatch trap crash ngay.

Nguy hiểm nhất là deadlock trên background thread hoặc cooperative pool, vì nó im lặng tuyệt đối và không hiện trong crash report."

● Trace từng dòng: vì sao gọi là "circular wait"?

Trước hết: hiểu "work item" là gì

Đây là mấu chốt nhiều người thiếu. viewDidLoad không phải code chạy tự do — nó cũng đang nằm trong một work item của main queue.

Main queue giống một hàng đợi các phong bì công việc. Main thread là một người duy nhất, lấy từng phong bì ra làm, làm xong mới lấy phong bì tiếp theo.

MAIN QUEUE:  [ viewDidLoad ] [ xử lý chạm ] [ vẽ lại màn hình ] ...
                    ↑
             main thread đang mở phong bì này

Quy tắc sống còn: main thread không bao giờ lấy phong bì tiếp theo khi phong bì hiện tại chưa làm xong. Đó chính là nghĩa của "serial".

Đoạn code

override func viewDidLoad() {          // dòng 1
    super.viewDidLoad()                // dòng 2
    print("A")                         // dòng 3
    DispatchQueue.main.sync {          // dòng 4
        print("B")                     // dòng 5
    }                                  // dòng 6
    print("C")                         // dòng 7
}                                      // dòng 8

Dòng 3 — in "A"

Console: A
QUEUE:   [ viewDidLoad ]  ← vẫn đang chạy, chưa xong

Dòng 4 — chỗ chết. main.sync làm HAI việc

Việc 4a — xếp block vào cuối main queue:

QUEUE:   [ viewDidLoad ] [ block in ra B ]
              ↑                  ↑
        đang chạy          vừa xếp vào, đứng chờ tới lượt

Việc 4b — main thread đứng lại chờ block đó chạy xong:

THREAD:  ⏸ ĐỨNG CHỜ block "in ra B" hoàn thành

Nhìn kỹ tình trạng

┌─────────────────────────────────────────────┐
│ MAIN QUEUE                                  │
│                                             │
│  [ viewDidLoad ]  ⏸ đang chờ block B xong   │
│  [ block in B  ]  ⏸ đang chờ tới lượt mình  │
│                                             │
└─────────────────────────────────────────────┘

Đọc hai câu này thật chậm:

  • block in B khi nào được chạy? → Khi viewDidLoad kết thúc. Vì serial queue chỉ chạy một việc một lúc.
  • viewDidLoad khi nào kết thúc? → Khi nó đi qua được dòng 4. Mà dòng 4 đang chờ block in B.
        chờ
  ┌──────────────────┐
  │                  ▼
[viewDidLoad]   [block in B]
  ▲                  │
  └──────────────────┘
        chờ

"Circular" = vòng tròn. Mũi tên "chờ" đi một vòng rồi quay về đúng chỗ xuất phát. Dòng 5, 6, 7 không bao giờ chạy — console chỉ có A.

Vì sao async thoát được

async chỉ làm một việc: xếp block vào queue rồi đi tiếp ngay. viewDidLoad kết thúc bình thường → main thread bỏ phong bì xuống → giờ mới tới lượt block kia.

Console: A → C → B

Khác biệt duy nhất: async không tạo ra sự phụ thuộc ngược.

Ẩn dụ hàng đợi

Bạn đứng ở quầy thanh toán, tới lượt mình rồi, nhưng nói với nhân viên: "Chờ đã, tôi muốn người xếp sau tôi được thanh toán xong trước, rồi tôi mới thanh toán."

Người sau chỉ được gọi khi bạn rời quầy. Bạn chỉ rời quầy khi người sau xong. Cả hàng đứng im — không phải vì ai sai, mà vì hai điều kiện loại trừ nhau.

● Quy tắc kiểm tra nhanh: khi nào .sync gây deadlock?

.sync KHÔNG chờ hàm chứa nó. Nó chỉ làm đúng một việc: dừng thread hiện tại, chờ cho tới khi block bên trong chạy xong. Vấn đề nằm ở câu hỏi thứ hai, tách biệt hoàn toàn: cái block đó bao giờ được phép bắt đầu?

someQueue.sync { doWork() }
   ↑        ↑
   │        └── Câu 2: thread gọi dừng lại chờ block xong
   └─────────── Câu 1: block xếp vào ĐÂY — bao giờ tới lượt nó?

Deadlock chỉ xảy ra khi câu 1 đòi hỏi hàm hiện tại kết thúc. Mà điều đó chỉ đúng trong một trường hợp: queue đích chính là serial queue mà code hiện tại đang chạy trên đó.

Test một câu

Khi thấy X.sync { }, hỏi: "Code tôi đang viết đây có đang chạy trên chính queue X không?"

Có → deadlock.  ·  Không → an toàn.

// Đang ở main thread:
DispatchQueue.main.sync { }        // ❌ đúng là queue mình đang đứng
DispatchQueue.global().sync { }    // ✅ queue khác

// Đang ở background thread:
DispatchQueue.main.sync { }        // ✅ main queue rảnh, chạy được
DispatchQueue.global().sync { }    // ✅ concurrent, luôn có chỗ

Concurrent queue thì sao?

Kể cả sync vào chính queue đang đứng, nếu nó là concurrent thì vẫn ổn — vì concurrent queue không bắt việc sau đợi việc trước:

let q = DispatchQueue(label: "q", attributes: .concurrent)
q.async {
    print("1")
    q.sync { print("2") }    // ✅ chạy được
    print("3")
}
// In: 1 → 2 → 3. Bỏ .concurrent đi → chết ngay.

5. Ba ngộ nhận hay gặp

Ba chỗ mà cách nói thông thường dễ dẫn tới hiểu sai. Gỡ được thì phần lớn câu hỏi GCD trở nên dễ.

● "Đọc song song thì phải dùng async chứ sao lại sync?"

Đây là chỗ ghép hai trục vào làm một. Tách ra là sáng ngay.

queue.sync { }
  ↑      ↑
  │      └── Trục 2: NGƯỜI GỌI có đứng chờ không?
  └───────── Trục 1: QUEUE này có cho nhiều việc chạy cùng lúc không?
  • Song song hay không → do queue quyết định (serial vs concurrent)
  • Người gọi chờ hay không → do sync/async quyết định

sync không làm mất tính song song. Nó chỉ nói "thread gọi tôi đứng đây chờ block của tôi xong" — nó không cấm thread khác chạy block của họ cùng lúc.

Lý do bắt buộc phải là sync: cần giá trị trả về

func get(_ key: String) -> Data? {
    queue.async {
        return storage[key]      // ❌ return cho closure, không phải cho get
    }
    return ???                   // ❌ hàm đã chạy tới đây, chưa có dữ liệu
}

Muốn dùng async thì phải đổi chữ ký hàm thành callback — bất tiện hơn nhiều. Còn set dùng async được vì nó không cần trả về gì.

Vậy song song nằm ở đâu?

Nằm ở chỗ nhiều thread khác nhau cùng gọi get:

Thời gian →

Thread A:  gọi get("a") ──⏸chờ──→ [đọc a] ─→ nhận kết quả
Thread B:  gọi get("b") ──⏸chờ──→ [đọc b] ─→ nhận kết quả
Thread C:  gọi get("c") ──⏸chờ──→ [đọc c] ─→ nhận kết quả
                                   ↑
                        BA BLOCK NÀY CHẠY CÙNG LÚC
                        vì queue là concurrent

Mỗi thread chờ block của chính nó. Nhưng ba block không chờ nhau. Nếu queue là serial, cùng đoạn code đó sẽ phải xếp hàng.

Serial queueConcurrent queue
syncChờ, chạy tuần tựChờ, nhưng chạy song song với caller khác
asyncKhông chờ, chạy tuần tựKhông chờ, chạy song song

Ô góc trên bên phải chính là trường hợp của get — ô mà nhiều người không hình dung ra.

Lợi ích phụ ít người biết

Khi bạn gọi queue.sync, GCD thường chạy thẳng block đó trên chính thread đang gọi — vì dù sao thread đó cũng đang đứng chờ. Nên queue.sync { storage[key] } rẻ hơn bạn tưởng, không có chi phí chuyển ngữ cảnh. Đó là lý do pattern này đủ nhanh cho cache truy cập liên tục.

Câu chốt để nhớ

sync/async quyết định "tôi có chờ không". serial/concurrent quyết định "chúng tôi có chạy cùng lúc được không".

get dùng sync vì nó cần giá trị trả về. get chạy song song được vì queue là concurrent. Hai điều đó không mâu thuẫn.

● "enter/leave nghĩa là phải chạy tuần tự?"

Không. Cả group.async và enter/leave đều chạy song song y hệt nhau. Vấn đề không nằm ở chạy thế nào, mà ở group biết lúc nào là "xong".

Chứng minh vẫn song song

let group = DispatchGroup()
let start = Date()

for i in 1...3 {
    group.enter()
    print("\(i) bắt đầu — \(Date().timeIntervalSince(start))")
    api.fetch(i) { _ in
        print("\(i) xong — \(Date().timeIntervalSince(start))")
        group.leave()
    }
}
group.notify(queue: .main) { print("tất cả xong") }

1 bắt đầu — 0.001
2 bắt đầu — 0.001     ← cả ba khởi động gần như cùng lúc
3 bắt đầu — 0.002
2 xong — 0.8          ← xong không theo thứ tự
1 xong — 1.2
3 xong — 1.5
tất cả xong — 1.5     ← tổng = cái lâu nhất, không phải tổng các phần

Ba API mất 1.2 + 0.8 + 1.5 = 3.5 giây nếu chạy lần lượt. Ở đây chỉ mất 1.5 giây. enter/leave chỉ là hai lời khai báo "tôi bắt đầu" và "tôi xong rồi" — chúng không chặn ai, không xếp hàng ai.

Diễn đạt lại cho chuẩn

group.async tự động báo "xong" khi closure kết thúc. Nếu bên trong closure có callback bất đồng bộ thì closure kết thúc trước khi công việc thật sự xong — group báo sớm.

enter/leave cho phép mình tự chọn thời điểm báo xong, đặt nó vào trong callback. Khác biệt duy nhất là mốc thời gian tính là hoàn thành.

● "Thấy .sync là nó luôn chờ hàm chứa nó chạy xong?"

Không. Chỉ khi queue đích là chính serial queue mà code hiện tại đang chạy trên đó.

Cách nói chuẩn: block phải đợi queue đích rảnh mới được chạy. Hàm chứa nó hoàn toàn không liên quan. Chỉ có một tình huống khiến hai thứ trùng nhau — khi queue đích chính là queue đang chạy hàm hiện tại, thì "queue rảnh" đồng nghĩa với "hàm hiện tại xong". Lúc đó mới thành vòng tròn.

Đang ở main thread, gọi…Queue đíchKết quả
DispatchQueue.main.syncMain queue — đang bận chạy hàm hiện tạiVòng tròn → chết
DispatchQueue.global().syncGlobal queue — đang rảnhChạy ngay → OK
DispatchQueue(label:"q").syncQueue mới — chưa chạy gìChạy ngay → OK

Bằng chứng rõ nhất: cùng một lệnh main.sync, gọi từ main thread thì crash, gọi từ background thread thì chạy ngon. Vấn đề không nằm ở sync, cũng không nằm ở "hàm chứa nó" — mà ở quan hệ giữa nơi bạn đang đứng và queue bạn nhắm tới.

6. Cách trả lời khi phỏng vấn

Nguyên tắc vàng

Chỉ dùng thuật ngữ nào mà nếu bị hỏi ngược "cái đó là gì?" bạn trả lời được trong hai câu. Ném "cooperative pool", "continuation-passing", "Coffman conditions" mà không giải thích được thì interviewer sẽ nghĩ bạn học thuộc.

Cấu trúc an toàn cho mọi câu

kết luận trước
    → giải thích bằng hình ảnh đời thường
        → ví dụ trong dự án của bạn
            → thuật ngữ đặt cuối, như nhãn dán

Bốn điều nên tránh

  • Đừng liệt kê bảng so sánh bằng miệng. "GCD thì thế này, Combine thế kia" nghe như đọc bài. Kể theo mạch: vấn đề gì → giải pháp nào ra đời để xử lý.
  • Đừng dùng từ tiếng Anh khi có từ tiếng Việt tự nhiên hơn. "Suspend" → "tạm dừng và cất lại". "Cooperative" → "các task tự nguyện nhường nhau".
  • Luôn gắn vào kinh nghiệm thật. "Trong dự án cũ em từng gặp…" có giá trị gấp nhiều lần định nghĩa sách vở. Interviewer muốn biết bạn đã va phải vấn đề chưa.
  • Khi không chắc thì nói thẳng. "Chỗ này em chưa đi sâu, em mới dùng ở mức cơ bản" an toàn hơn nhiều so với đoán bừa rồi bị hỏi tiếp.

Hai câu bẫy kinh điển

"async có nghĩa là chạy song song không?"
Không. async chỉ nghĩa là "không chờ". Nếu queue đích là serial thì các block vẫn chạy lần lượt.

"Dùng sync có luôn chậm hơn async không?"
Không. sync không có chi phí chuyển ngữ cảnh nếu chạy được ngay. Vấn đề của sync là rủi ro deadlock, không phải hiệu năng.

Điều rút ra chung: phần lớn câu hỏi GCD đều xoay quanh việc bạn có tách được hai trục độc lập hay không — ai chờ ai (sync/async) và bao nhiêu việc chạy cùng lúc (serial/concurrent). Gộp hai trục làm một là nguồn gốc của gần như mọi câu trả lời sai.
