1. Swift Language Core

● Q1.1 — Value type vs Reference type. What's the difference?

Core: - Value type (struct, enum, tuple): copied on assignment/passing. Each variable holds its own independent copy. - Reference type (class, actor, closure): passed by reference (pointer). Multiple variables can point to the same instance on the heap.

VALUE TYPE (struct)                REFERENCE TYPE (class)
┌──────────┐                       ┌──────────┐      ┌──────────┐
│ var a    │──► [x:1, y:2]         │ var a    │──┐   │          │
├──────────┤                       ├──────────┤  ├──►│ Heap obj │
│ var b=a  │──► [x:1, y:2] (copy)  │ var b=a  │──┘   │ [x:1]    │
└──────────┘                       └──────────┘      └──────────┘
  changing b does NOT affect a       changing b AFFECTS a (same obj)

Common trap questions: - Does a struct live on the stack or heap? → Usually stack, but if the struct contains a reference type or is captured by an escaping closure, that part still lives on the heap. - Copy-on-Write (COW): Array, Dictionary, String are structs but do NOT copy immediately on assignment — they only copy on actual mutation. This is a stdlib optimization, not something you get automatically for your own structs.

When to choose struct vs class? - Struct: data model, immutable, no need for identity, no inheritance. - Class: needs identity (compare with ===), needs inheritance, needs lifecycle (deinit), Objective-C interop.

Go deeper

Why does Swift default to struct instead of class like most OOP languages?

Because the default should be the safe one. A value type has no shared mutable state, so it cannot be mutated behind your back by another owner and cannot participate in a retain cycle. That removes an entire class of bugs (aliasing, data races, leaks) before you write a line of code.

It also unlocks performance: no heap allocation, no ARC traffic, no dynamic dispatch, and the compiler can keep small structs in registers. You reach for class when you actually need what it adds — identity, inheritance, deinit, Obj-C interop — and pay the cost knowingly.

If value types are so good, why not use them everywhere? What do you lose?

Three things you sometimes need:

  • Identity. Two structs with equal fields are indistinguishable. A UserSession or a network connection is a specific thing — you need ===, not ==.
  • Shared mutation. When many parts of the app must observe the same object (a cache, a store), copies are exactly the wrong semantics.
  • Lifecycle. Only a class has deinit — needed to close a file, cancel a task, remove an observer.

And a large struct copied through many layers can cost more than one retain/release. Size matters: a 200-byte struct passed around a hot loop is a real memcpy.

Why does Copy-on-Write exist — what problem would we have without it?

Without COW, value semantics on collections would be unusable: every let b = bigArray would deep-copy a million elements just to read it. COW gives you the safety of value semantics at the cost of reference passing — the buffer is shared until someone writes, and only then does isKnownUniquelyReferenced trigger a real copy.

Interview payoff: this is why you can pass Array freely, and also why an in-place array[i] = x inside a loop is cheap but let copy = array; copy.append(x) in a loop is not.

How does this actually change decisions in a real app?

Concrete rules I apply: DTOs / domain models decoded from JSON → struct (cheap, Sendable, testable by equality). SwiftUI state → struct, because SwiftUI diffs by value and a class would silently skip re-renders. View models, repositories, caches, coordinators → class/actor, because they own identity and lifecycle.

The payoff is not academic: value models are what make Sendable checking and Swift 6 strict concurrency pass without a fight.

● Q1.2 — What is Protocol-Oriented Programming (POP)? How does it differ from OOP?

Core: Favors composition through protocol + protocol extension instead of class inheritance. The Swift stdlib is designed this way (Collection, Equatable...).

protocol Drawable {
    func draw()
}

// Protocol extension: provides a default implementation
extension Drawable {
    func draw() { print("Default drawing") }
}

struct Circle: Drawable {}   // uses the default
struct Square: Drawable {    // overrides
    func draw() { print("Square") }
}

Senior trap — Static vs Dynamic dispatch in a protocol extension:

protocol Greet { func hello() }
extension Greet {
    func hello() { print("protocol hello") }
    func bye()   { print("protocol bye") }  // NOT declared in the protocol
}
struct A: Greet {
    func hello() { print("A hello") }
    func bye()   { print("A bye") }
}

let a: Greet = A()
a.hello()  // "A hello"      → hello() is in the protocol → dynamic dispatch
a.bye()    // "protocol bye" → bye() is NOT in the protocol → static dispatch based on the static type (Greet)

→ A method declared in the protocol = dynamic dispatch (resolved by the actual runtime type). → A method only in the extension = static dispatch (resolved by the declared/static type). This is the classic question that traps newcomers.

Go deeper

Why prefer protocol + extension over a base class? What was actually wrong with inheritance?

Class inheritance forces a single, vertical hierarchy: one superclass, decided at declaration time, carrying its state with it. Real requirements are horizontal — a type may need to be Codable, Cacheable, and Loggable at once. With inheritance you either build a god base class or duplicate code.

Protocols compose (a type conforms to many), work on struct/enum (so you keep value semantics), and carry no stored state — so you never inherit fields you don't want.

What does POP buy me concretely, beyond being “cleaner”?

Testability is the big one: depend on protocol APIClient and you can inject a stub with no subclassing, no mocking framework, no Obj-C runtime tricks. Retroactive modeling is the second: you can conform a type you don't own (String, URLSession) to your protocol in an extension.

And default implementations in extensions let you add a method to 20 conformers at once without touching them — that's how Collection gives you map/filter for free.

When would you deliberately not use POP and pick a class hierarchy instead?

When the framework demands it (UIViewController, UIView — you must subclass), when you need shared stored state and identity across the family, or when a protocol with associated types would infect the whole codebase with generics for no gain. Over-protocolizing produces one-conformer protocols that add indirection and hurt readability — a real senior signal is knowing when to stop.

Why does the static/dynamic dispatch trap matter in production, not just in quizzes?

Because it silently changes behaviour. If a method exists only in the extension and a conformer “overrides” it, calls through the protocol type run the extension's version — your override is dead code. That shows up as a bug you can't explain: the right code exists, it just never runs.

Rule: if you intend it to be overridable, declare it in the protocol. The extension is then a default, not a shadow.

● Q1.3 — some vs any (opaque type vs existential)

 
func makeShape() -> some Shape { Circle() }   // opaque: 1 specific concrete type, hidden from the caller
func makeShape() -> any Shape { ... }          // existential: dynamic box, can hold multiple types
  • some: the compiler knows the exact concrete type (only hidden from the caller) → no overhead, optimizes well.
  • any: existential container, has runtime overhead (dynamic dispatch + possible heap allocation). Use when you need to store multiple different types in one array.

Go deeper

Why did Swift add some at all — what was impossible before?

Before opaque types you had to choose between leaking your implementation type in the signature (-> LazyMapSequence<...>, awful to maintain) or boxing into an existential and paying runtime cost. some gives a third option: the caller sees an abstract type, the compiler sees the concrete one.

It also made SwiftUI possible — var body: some View hides a deeply nested generic tree while keeping full static specialization.

Why not just use any everywhere and keep things simple?

Three costs. Performance: an existential is a box — dynamic dispatch through a witness table, and heap allocation if the value exceeds the inline buffer (3 words). Lost type identity: any Equatable == any Equatable doesn't compile, because the compiler can't prove both sides are the same type. Associated types: with any Collection you lose Element unless you use primary associated types (any Collection<Int>).

So: some by default, any when heterogeneity is the actual requirement.

Give me the decision rule you'd say out loud in an interview.

“One concrete type per call site → some. Many different types stored together, or a type decided at runtime → any.” A [any Shape] holding circles and squares is correct use. A function returning any Shape when it always returns Circle is just paying tax.

Also worth saying: Swift 5.7+ made any explicit precisely so this cost stops being invisible — the keyword is a warning label.

● Q1.4 — Optional. if let / guard let / ?? / optional chaining

 
guard let user = user else { return }   // early exit, keeps the scope flat
if let user { ... }                      // shorthand (Swift 5.7+)
let name = user?.name ?? "Guest"         // nil-coalescing

Trap: try? turns an error into nil (swallows the error). as? is a conditional cast. Avoid force unwrap ! unless you're 100% certain.

Go deeper

Why does Swift have Optional at all instead of nullable references like Java/Kotlin?

Because it moves nil from a runtime surprise to a compile-time fact. Optional is just an enum { case none, some(Wrapped) } — nothing magic — so the type system can force you to handle the empty case. No implicit null, no NPE at 2am.

The payoff is documentation for free: func find(id:) -> User? tells the caller “may not exist” without a comment, and the compiler enforces it.

Why prefer guard let over if let? Isn't it the same thing?

Not the same in two ways. guard must exit the scope in its else, so the compiler guarantees the happy path continues at the top level of the function — no nesting pyramid. And the unwrapped value stays in scope after the guard, which if let can't do.

Practical rule: guard for preconditions at the top of a function; if let when both branches are genuinely meaningful.

Why is force unwrap so hated? Is there ever a legitimate use?

! converts a recoverable condition into a crash, and crash reports rarely tell you which optional. It's hated because it's usually laziness in place of a decision.

Legitimate uses exist: an @IBOutlet after view load, a resource you ship in the bundle, or a programmer-error invariant where crashing early is better than corrupting data. In those cases prefer a documented crash — guard let x else { preconditionFailure("...") } — so the failure message names the cause.

Why is try? considered dangerous when it looks so convenient?

It collapses “failed, and here's why” into a bare nil. You lose the error, so you can't log it, retry intelligently, or show the user a real message — and a network failure becomes indistinguishable from an empty result. Use it only where the reason genuinely doesn't matter (a best-effort cache read); otherwise do/catch and keep the error.

● Q1.5 — escaping vs non-escaping closure
  • Non-escaping (default): the closure finishes being called within the function's scope.
  • @escaping: the closure is stored and called after the function returns (completion handler, stored property). → Requires explicit self. → easy to create a retain cycle.
func load(completion: @escaping (Data) -> Void) {
    URLSession.shared.dataTask(with: url) { data, _, _ in
        completion(data!)   // escaping because it runs after load() returns
    }.resume()
}

Go deeper

Why is non-escaping the default? What does the compiler gain?

Because if the compiler knows the closure cannot outlive the call, it can keep the closure's context on the stack — no heap box, no ARC on captured values — and it can guarantee captures are still valid, which is why you don't need explicit self. and can't create a retain cycle.

That's a real optimization: map, filter, sort are all non-escaping, so tight loops over collections don't allocate.

Why does @escaping force explicit self.?

It's a deliberate speed bump. Storing the closure means storing whatever it captured, so self would be retained for an unknown lifetime. Requiring you to write self. makes the capture visible at the call site, which is exactly where you should decide between [weak self] and a strong capture.

Why not just always write [weak self] and stop thinking about it?

Because sometimes you want the work to finish. If a save operation captures self weakly and the view controller is dismissed, the write silently never happens. Strong capture is correct for fire-and-forget work that must complete; [weak self] is correct when the result is only useful if the UI is still alive.

Also [weak self] everywhere breeds guard let self else { return } noise and hides real ownership decisions behind a reflex.

Where has async/await changed this picture?

A lot of escaping-closure pain disappears: with await there's no stored callback to leak, and self is held only for the duration of the suspension, so structured concurrency handles the lifetime. The new hazard moves to task cancellation — a Task { } that captures self strongly keeps the object alive until it finishes, so you store the task and cancel it in deinit/onDisappear instead.

2. Memory Management (ARC)

● Q2.1 — How does ARC work?

Core: Automatic Reference Counting. Each object holds a retain count. +1 when a new strong reference appears, -1 when one is lost. Count = 0 → deinit → released. Compile-time, not a runtime garbage collector like Java/Kotlin.

strong ref +1 ──► retainCount = 2
                       │
    nil / out-of-scope │ -1
                       ▼
                  retainCount = 0 ──► deinit() ──► freed

Go deeper

Why did Apple choose ARC over a tracing garbage collector?

Determinism and footprint. ARC frees an object the moment the last reference goes away, so memory use is predictable and deinit runs at a known point — which matters on a battery-powered device with hard frame deadlines. A tracing GC introduces pauses and needs headroom (typically ~2× live memory) that phones don't have to spare.

The trade is that ARC can't collect cycles, so you own that problem — hence weak/unowned.

If ARC is “compile-time”, why does it still cost anything at runtime?

The decision of where to insert retain/release is compile-time; the counter updates are real runtime work, and they must be atomic because objects can be shared across threads. In hot paths that's measurable — which is exactly the argument for value types, which have no refcount at all.

The optimizer removes a lot of it (ownership conventions, @guaranteed parameters, retain/release pairing), which is why release builds can be dramatically faster than debug here.

Why does deinit matter — isn't “memory is freed” enough?

Because deinit is your only deterministic hook for non-memory resources: cancel a Task, close a socket, stop a timer, remove a NotificationCenter observer, release a file handle. Getting this wrong doesn't show up as a leak — it shows up as duplicate callbacks, a timer firing after the screen is gone, or a file that stays locked.

● Q2.2 — Retain cycle. weak vs unowned. (a staple question)

Retain cycle: 2 objects hold a strong reference to each other → the count never reaches 0 → memory leak.

┌─────────────┐  strong  ┌─────────────┐
│  ViewModel  │─────────►│   Closure   │
│             │◄─────────│  (captures  │
└─────────────┘  strong  │   self)     │
      LEAK               └─────────────┘

Solution — capture list:

// weak: reference can become nil → use when the other object might be deallocated first
service.fetch { [weak self] result in
    guard let self else { return }
    self.handle(result)
}

// unowned: assumes the other object is ALWAYS still alive → if wrong → CRASH
button.action = { [unowned self] in self.tap() }
weak unowned
Optional Yes (auto becomes nil) No
When the other object is deallocated Safe (nil) Crash if accessed
Use when Lifecycle is uncertain Certain same lifetime (e.g. required parent-child)

Rule of thumb: when unsure → use weak. unowned only when you are CERTAIN the other reference outlives the closure at least as long.

Delegate is always weak:

weak var delegate: MyDelegate?   // avoid a cycle between parent ↔ child

→ That's why delegate protocols are usually : AnyObject (only classes can be weak).

Go deeper

Why does weak have to be Optional, and why does that make it slower than unowned?

weak promises to become nil when the target dies, so the runtime keeps a side table mapping the object to its weak references and zeroes them on deallocation. That bookkeeping (plus the optional check on every access) is the cost. unowned keeps no such record — it's just a non-owning pointer — so it's cheaper but dangles if you're wrong.

If unowned is faster, why is weak the recommended default?

Because the failure modes are not symmetric. Getting weak wrong gives you a nil you can handle; getting unowned wrong gives you a crash on a freed object — often intermittently, in production, in a stack trace that blames the wrong line.

Use unowned only when the lifetime relationship is a genuine invariant: the reference can never outlive the target (a child that cannot exist without its parent). Otherwise weak, and pay the nanoseconds.

Why don't delegates cause a cycle when they're weak — and why is that the convention?

Because ownership is one-directional by design: the parent owns the child strongly, the child points back weakly. Making delegate strong creates the textbook A↔B cycle where neither is ever released, and the symptom is subtle — screens that “work fine” but never deinit, so memory climbs the longer the session runs.

Say the rule out loud: the owner is strong, the observer is weak.

Which closure captures actually leak, and which are safe? People over-apply [weak self].

A capture leaks only if the closure is stored by something self owns (a stored property, a subscription, a long-lived callback). Non-escaping closures (map, sort) and one-shot escaping closures that the system releases when done (URLSession completion, DispatchQueue.async) don't create a permanent cycle — at worst they delay deallocation.

So the question to ask is not “is it escaping?” but “who holds this closure, and for how long?”

● Q2.3 — How do you detect a memory leak?
  • Xcode Memory Graph Debugger (the debug memory graph button) → look at the reference cycle.
  • Instruments → Leaks / Allocations.
  • Put a print / breakpoint in deinit → if a view controller is popped but deinit is never called → there's a leak.

Go deeper

Why isn't “memory keeps growing” enough to conclude there's a leak?

Because caches, image decoding buffers, Core Data's row cache and URL cache all grow on purpose. A leak is memory that is unreachable-but-retained and never reclaimed. The way to distinguish them: exercise a flow repeatedly (push/pop a screen 5 times) and check whether the baseline returns — a cache plateaus, a leak steps up each cycle.

Why is a deinit print often better than Instruments in practice?

Because it answers the exact question — “did this object die?” — in one line, with zero setup, and it works in CI and on device. Instruments tells you what is retained; a deinit breadcrumb tells you whether the object you care about was released at the moment you expected. Start there, escalate to the Memory Graph Debugger when the answer is no and you need the retain path.

What does the Memory Graph Debugger give you that a leak count can't?

The retain path: who is holding the object, through which property, in which cycle. That's the only information that actually tells you where to put weak. A leak count tells you that you have a problem; the graph tells you which line to change.

How would you stop leaks from coming back, rather than fixing them one by one?

Turn the check into a test: in teardown, hold a weak var to the subject and assert it's nil after the strong reference is dropped. That's a leak test you can run in CI for every view model and coordinator. Combine with Address Sanitizer / Zombie Objects in the scheme for use-after-free, and the class of bug stops regressing silently.

Go deeper

Why did Apple build Swift Concurrency when GCD already worked?

GCD is correct but unstructured: nothing ties a queue hop to the code that started it, so cancellation, error propagation and “wait for these three things” are all hand-rolled. And it's easy to write code that looks fine and deadlocks or over-commits threads.

Swift Concurrency adds three things GCD can't: structured lifetimes (a child task cannot outlive its parent), compile-time data-race checking via Sendable/actors, and a cooperative thread pool capped at the core count.

What is thread explosion, and why can't it happen with async/await?

With GCD, a blocked thread still occupies a thread. Dispatch responds by spinning up more — dozens or hundreds — and you pay in context switches and memory until the app crawls. That's thread explosion, and it's the classic outcome of DispatchQueue.global().async in a loop with blocking work inside.

await is a suspension, not a block: the task's continuation is parked and the thread goes back to the pool. So N concurrent tasks need N continuations, not N threads.

If Swift Concurrency is better, why is GCD still in every codebase — and when do you keep it?

Practical reasons: it's available on older OS versions, it's already threaded through legacy code, and some APIs are still callback-based. And a few things it genuinely does well have no direct replacement in the same shape — DispatchSourceTimer, dispatch I/O, precise queue targeting for a C library, or a quick DispatchQueue.main.async in UIKit code.

The senior answer is “new code async/await, bridge legacy with continuations, don't rewrite for its own sake” — and never mix the two on the same state without a clear owner.

Why is calling DispatchSemaphore.wait() inside an async function dangerous?

Because it blocks a cooperative-pool thread, and that pool is intentionally tiny (one thread per core). Block a few and you can starve or deadlock the entire concurrency runtime — including the continuation that would have signalled the semaphore. This is the single most common “it works on my simulator, it hangs on device” bug when teams migrate.

● Q3.2 — async/await, Task, async let, TaskGroup

 
// Sequential
let user = try await fetchUser()
let posts = try await fetchPosts()

// Parallel, fixed count → async let
async let user = fetchUser()
async let posts = fetchPosts()
let profile = Profile(user: try await user, posts: try await posts)

// Parallel, dynamic count → TaskGroup
try await withThrowingTaskGroup(of: Post.self) { group in
    for id in ids { group.addTask { try await fetchPost(id) } }
    for try await post in group { results.append(post) }
}

Structured vs Unstructured:

async let / TaskGroup Task { }
Kind Structured Unstructured
Lifetime Bound to the parent scope Independent, can outlive the function
Cancel Auto-propagates Doesn't auto-follow the parent
Must await Yes (compiler-enforced) No (can fire-and-forget)

Task { } ≈ DispatchQueue.async { } in purpose, but Task {} automatically inherits the actor context + has standardized cancellation. Task.detached {} is the one that's really like plain GCD (inherits nothing).

Go deeper

Why choose async let over TaskGroup — or the reverse?

async let is for a fixed, known set of concurrent operations with different types: two or three fetches you then combine. It reads like straight-line code and the compiler tracks each result's type.

TaskGroup is for a dynamic count of same-shaped work: “download these N images”, where N comes from data. It also lets you consume results as they arrive and apply throttling. Using a group for two fixed calls is over-engineering; using async let in a loop is impossible.

Why is a bare Task { } considered a code smell in a view model?

Because it's unstructured: it escapes the current task tree, so it doesn't inherit cancellation and nothing will stop it when the screen goes away. It also captures self strongly for its lifetime. The result is work that runs after dismissal, updates dead state, or double-fires on rapid navigation.

Fixes: store the task and cancel it, use .task {} in SwiftUI (which cancels on disappear automatically), or make the function async and let the caller own the lifetime.

Why must cancellation be cooperative? Why can't Swift just kill the task?

Because a killed task could leave half-written files, an unbalanced lock, or a database in an inconsistent state. So cancellation only sets a flag; your code decides where it's safe to stop, by checking Task.isCancelled or calling try Task.checkCancellation() at a safe point.

The practical consequence: a task with a long loop and no checks is uncancellable, and you'll see “stop” buttons that don't stop anything.

What does structured concurrency actually buy you day to day?

Three guarantees that used to be manual work: a parent cannot return before its children finish (no orphaned work), cancellation propagates down the tree automatically (one cancel stops the whole subtree), and an error thrown by a child cancels its siblings and surfaces at the parent's await. That's the entire retry/timeout/cleanup boilerplate you used to write by hand.

● Q3.3 — Actor, MainActor, Sendable

 
actor Cache {              // serial access, no lock needed, compiler prevents races
    private var store: [String: Data] = [:]
    func get(_ k: String) -> Data? { store[k] }
}

@MainActor                 // everything runs on the main thread — standard for a ViewModel
final class ProfileVM: ObservableObject {
    @Published var posts: [Post] = []
}

Actor reentrancy (senior trap): between 2 await points in a single actor method, state can be mutated by another method slipping in. await = a suspension point = the actor can service another request. → Always re-check state after every await inside an actor.

Sendable: a protocol marking a type as safe to pass across an actor boundary. In Swift 6 strict mode → passing a non-Sendable type across a boundary is a build error. - A struct with Sendable properties → automatically Sendable. - A class → must be immutable, or @unchecked Sendable + handle thread-safety yourself (lock/actor).

nonisolated: opts out of isolation for a method that doesn't touch state (pure function) inside a @MainActor class.

Go deeper

Why an actor instead of a lock or a serial queue? They all serialize access.

They serialize, but only the actor makes it impossible to forget. A lock protects state only if every single access remembers to take it — one missed path is a race. With an actor, isolation is part of the type: the compiler rejects any external access that isn't awaited.

The second difference is that actors suspend rather than block. A thread waiting on a lock is a wasted thread; a task awaiting an actor releases its thread back to the pool.

What is actor reentrancy, and why did Apple choose it despite the bugs it enables?

An actor releases its isolation at every await, so another message can run in between. That's deliberate: without it, one slow network call inside an actor method would block the actor for everyone — and it makes deadlock much harder to create.

The price is that your assumptions may be stale after an await. So re-check state after suspension, and don't treat a whole actor method as atomic — the classic bug is checking a cache, awaiting a fetch, then writing unconditionally and doing the work twice.

Why do we need @MainActor when we already had DispatchQueue.main.async?

Because it moves “must be on the main thread” from a convention you remember to a property the compiler checks. Annotate the view model and any off-main access becomes an error instead of a random UI glitch or a crash in UIKit.

It's also more efficient: no hop is emitted when you're already on the main actor, whereas DispatchQueue.main.async always defers to the next runloop turn.

What is Sendable really for, and why does it produce so many warnings?

It's the compiler's proof that a value can cross an isolation boundary safely — value types with sendable members qualify; a mutable class doesn't. The warnings are the compiler pointing at code that was already unsafe; they just used to be invisible until a crash on a user's device.

The intended fixes, in order: make the type a value type, make it an actor, or make immutability explicit (let only, final class). @unchecked Sendable is you signing a promise the compiler can't verify — acceptable with a lock, but write down why.

● Q3.4 — Continuation (bridging a callback → async)

 
// (T?, Error?) -> Void  →  withCheckedThrowingContinuation
func fetchUser() async throws -> User {
    try await withCheckedThrowingContinuation { c in
        legacyFetchUser { user, error in
            if let error { c.resume(throwing: error) }
            else if let user { c.resume(returning: user) }
            else { c.resume(throwing: URLError(.unknown)) }
        }
    }
}

Rule: resume() must be called exactly once — calling it twice or forgetting to call it → crash (the Checked variant) / undefined behavior (the Unsafe variant). Choose: - Callback with no Error → withCheckedContinuation - Callback with Error / Result → withCheckedThrowingContinuation (use resume(with:) for Result)

Go deeper

Why do we need continuations at all — why not rewrite the callback API?

Because you often can't: it's a system framework, a C library, a delegate protocol, or 200k lines of legacy you don't own. A continuation is the seam that lets you adopt async/await at the edges and migrate inward incrementally, instead of a big-bang rewrite.

Why is resuming a continuation twice a crash rather than a warning?

Because a continuation represents a single suspension point; resuming it twice would mean returning from the same function call twice, which corrupts the task's state. Swift chooses a loud, deterministic crash over undefined behaviour.

Practical consequence: the classic bug is a callback that fires both a value and an error path, or a delegate that can be called repeatedly. Guard with a flag, and never bridge a multi-callback API with a continuation — that's what AsyncStream is for.

When do you pick AsyncStream over withCheckedContinuation?

Count the callbacks. One result → continuation. Many results over time → AsyncStream (location updates, socket messages, progress, notifications). Trying to force a stream of events through a continuation is exactly how you get the double-resume crash.

Why withCheckedContinuation instead of the unsafe variant?

The checked version adds runtime bookkeeping that traps on the two mistakes people actually make — resuming twice, and never resuming (which silently hangs the task forever). That's worth far more than the small overhead; switch to withUnsafeContinuation only if profiling proves it matters in a hot path.

Go deeper

Why does the “where do I put this code” question matter so much in the lifecycle?

Because each hook has a different guarantee. In viewDidLoad the view exists but has no final geometry — so frame math there is wrong. viewWillLayoutSubviews/viewDidLayoutSubviews is where bounds are real, but it can run many times per frame, so it must stay cheap and idempotent.

Put one-time setup in viewDidLoad, geometry in layout, and anything that should track visibility (start/stop) in viewWillAppear/viewDidDisappear.

Why is viewDidLoad the wrong place to start a timer or an observer?

Because it runs once, but a view controller can be shown and hidden many times. Subscribe there and you keep receiving updates (and burning battery) while the screen is off-screen or covered; you'll also double-subscribe when you fix it wrong.

Pair the lifecycle: start in viewWillAppear, stop in viewWillDisappear. Symmetry is the rule to state in an interview.

Why does “appear” not mean “visible”, and why does that matter?

viewWillAppear fires when the controller is being added to the hierarchy — but a partially-dragged interactive back swipe that gets cancelled, a modal presented on top, or an app going to background all break the intuition that appear ⇒ visible. Analytics that count screen views in viewDidAppear without dedupe are how teams end up with inflated numbers.

How does SwiftUI change how you think about all this?

SwiftUI replaces imperative lifecycle hooks with declarative state plus .onAppear/.onDisappear/.task, and .task notably ties work to the view's lifetime and cancels it automatically. Knowing the UIKit lifecycle still matters — because UIHostingController means SwiftUI screens sit inside it, and “my .onAppear ran twice” is usually a UIKit-side containment story.

● Q4.2 — UITableView optimization & Diffable Data Source

Cell reuse: dequeueReusableCell → reuses off-screen cells instead of creating new ones → saves memory. Remember to reset cell state in prepareForReuse().

Diffable Data Source (iOS 13+): replaces manual reloadData() with a snapshot → auto-animates the diff, avoids "inconsistent state" crashes, more thread-safe.

var snapshot = NSDiffableDataSourceSnapshot<Section, Item>()
snapshot.appendSections([.main])
snapshot.appendItems(items)
dataSource.apply(snapshot, animatingDifferences: true)

Go deeper

Why do cells get reused at all — what would happen without it?

Allocating and laying out a view per row means memory proportional to the data set and a hitch on every scroll. Reuse bounds the cost to what fits on screen: a 10,000-row table holds ~12 cells. The trade is that a cell arrives dirty, which is why prepareForReuse and unconditional configuration matter — the “wrong avatar on the wrong row” bug is always a reuse bug.

Why is Diffable Data Source better than reloadData()? reloadData always works.

reloadData() works and is also the reason for three real problems: it drops animation, it loses selection and scroll position, and it does full work for a one-row change. Diffable computes the minimum set of changes from identity, so you get correct animations for free.

More importantly it removes the class of crash where your model and numberOfRows disagree — “attempted to delete row 5 but there are only 4 rows” becomes structurally impossible, because there's one snapshot and it's the source of truth.

What breaks if your identifier isn't stable and unique?

Everything diffable gives you. Non-unique IDs crash outright (“duplicate identifiers”); IDs derived from mutable content mean an edit looks like delete+insert, so the row flickers, loses focus mid-typing, and animations look wrong. Rule: hash the identity (server id), never the content.

Where does scroll performance actually go, if not in the diffing?

Almost always three places: layout (deep Auto Layout hierarchies re-solved per cell — flatten, or cache heights), off-main work on the main thread (image decode, date formatting, JSON — move them off and cache the result), and offscreen rendering (cornerRadius + masksToBounds, shadows without shadowPath). Prefetching with UITableViewDataSourcePrefetching then hides the network latency.

● Q4.3 — Responder Chain

Touch/event goes up from the deepest view: UIView → superview → ... → UIViewController → UIWindow → UIApplication → AppDelegate. Whoever's canBecomeFirstResponder handles it first.

Go deeper

Why does iOS use a responder chain instead of delivering the event straight to a handler?

Because at touch time the system knows where you touched, not who should care. The chain lets the innermost view get first refusal and pass unhandled events outward, so a control can handle what it understands and let the container deal with the rest — without either knowing about the other. That's how one UIMenu or keyboard shortcut can work across an entire screen hierarchy.

Where does this actually help you in real code?

Three everyday wins: resignFirstResponder / view.endEditing(true) to dismiss the keyboard from anywhere; UIResponder.next walking to find an owning view controller instead of threading a delegate through five layers; and canPerformAction(_:withSender:) to add copy/paste or menu actions at the right level.

Why do touches sometimes “disappear” — and how does hit-testing relate?

Because the chain never starts. hitTest(_:with:) ignores views that are hidden, have alpha < 0.01, or have isUserInteractionEnabled = false, and it clips to bounds — so a button drawn outside its parent's bounds is untappable even though you can see it. Gesture recognizers add a second layer: they can cancel touches before your view ever sees them.

Debug order: is the view hit-testable → is something on top → is a gesture eating it.

● Q5.1 — Property wrappers & data flow
Wrapper Owns it? Use when

Classic trap — @StateObject vs @ObservedObject:

@ObservedObject: the object comes from outside → if the parent re-renders and recreates it → state is LOST

→ An object that the view itself instantiates → always @StateObject. Mistakenly using @ObservedObject → the object gets recreated on every redraw → data-loss bug.

iOS 17+ @Observable macro is gradually replacing ObservableObject/@Published — automatic tracking, less unnecessary re-rendering.

Go deeper

Why so many wrappers? Why not one “state” concept?

Because they encode ownership, and ownership is real information SwiftUI needs to decide what to re-render and what to keep alive across view rebuilds. @State = this view owns it. @Binding = someone else owns it, I can write to it. @StateObject = this view creates and owns a reference type. @ObservedObject = it was handed to me; I don't control its lifetime. @EnvironmentObject = injected from an ancestor.

Collapse them into one and SwiftUI either recreates your objects on every redraw or leaks them.

What actually goes wrong if you use @ObservedObject where @StateObject belongs?

The view recreates the object every time the body re-evaluates, because @ObservedObject doesn't own storage. Symptoms: state resets for no reason, network calls fire repeatedly, a loading spinner that never ends. It's one of the most common “SwiftUI is buggy” reports that is actually an ownership mistake.

Rule: the view that creates it uses @StateObject (or @State with @Observable); views that receive it use @ObservedObject (or a plain let).

Why did Apple introduce @Observable when ObservableObject worked?

Performance and ergonomics. With ObservableObject, any @Published change notifies every observing view, even ones that read none of the changed fields — so big view models cause wide over-rendering. @Observable tracks reads per property, so a view re-renders only if it actually read what changed.

It also deletes boilerplate: no @Published on every property, and @ObservedObject/@StateObject collapse into plain let/@State.

When is @EnvironmentObject the right tool, and what's the cost?

Right when a dependency is needed by many views at different depths (theme, session, router) and threading it through initialisers would pollute every layer. The cost is that it's resolved at runtime — forget to inject it and you crash on presentation, with no compile-time protection. So use it for genuinely app-wide things, and keep feature-level dependencies explicit in the initialiser.

● Q5.2 — View identity & lifecycle

SwiftUI's View is a value type describing the UI, not an actual object. SwiftUI diffs the view tree and only updates the parts that changed. Identity (.id(), structural position) determines whether a view is kept or recreated. body can be called multiple times → don't put heavy side-effects inside body.

Go deeper

Why does SwiftUI care about identity so much — it's just redrawing, isn't it?

No: SwiftUI has to decide, for every rebuild, whether a view is the same view with new data or a different view. Same view → keep its @State, animate the change. Different view → tear down state, run onDisappear/onAppear, no animation. Every “my state resets” or “my animation doesn't animate” bug is that decision going the other way from what you expected.

Why is id: \.self in a ForEach so often wrong?

Because it makes identity equal to content. Change a row's text and its identity changes, so SwiftUI deletes the old row and inserts a new one: state is lost, focus jumps out of the text field, and the animation reads as a replace instead of an update. And duplicate values collapse into one row. Use a stable, unique id from your model.

When would you deliberately use .id(...) to force a new identity?

When you actually want a reset: switching to a different user's profile, restarting a quiz, or forcing a view to rebuild after a locale change. It's a blunt tool — it throws away all the child state and cannot animate — so it's the right call for “this is now a different thing”, and the wrong call for “this thing changed”.

Why is expensive work in body a problem when body looks like it runs once?

Because body is a pure function SwiftUI may call many times per frame, for reasons you don't control. Sorting an array, formatting dates, or building a DateFormatter in there turns a redraw storm into dropped frames. Move it into the model, memoize it, or hoist it out — and put side effects in .task/.onAppear, never in body.

6. Combine

● Q6.1 — Publisher / Subscriber / Operator

 
Publisher ──► Operator(s) ──► Subscriber
 (emits)       (transforms)    (receives + demand)

searchText
    .debounce(for: .milliseconds(300), scheduler: RunLoop.main)  // avoid firing on every keystroke
    .removeDuplicates()
    .flatMap { query in self.api.search(query) }                 // switch streams
    .receive(on: DispatchQueue.main)                             // back to main to update the UI
    .sink { completion in ... } receiveValue: { results in ... }
    .store(in: &cancellables)                                    // keep the subscription alive

Trap: forgetting .store(in:) → the subscription is deallocated immediately → never receives a value. Use [weak self] in sink to avoid a retain cycle. receive(on:) differs from subscribe(on:): the former switches the thread for downstream, the latter for upstream/subscription.

Combine vs Swift Concurrency: Combine excels at streams of many values over time (UI binding, debounce). async/await excels at one-shot async (1 request → 1 result). The newer trend leans toward Concurrency + @Observable, but Combine is still common in existing codebases.

Go deeper

Why would you still use Combine now that async/await exists?

Because they solve different shapes. async/await is for one result (or a sequence you pull); Combine is for streams you react to with rich time-based operators — debounce, throttle, combineLatest, merge. A search field that debounces typing and cancels the in-flight request is three lines of Combine.

It's also unavoidable in practice: ObservableObject, NotificationCenter.publisher, and KVO publishers are Combine. Increasingly, though, AsyncStream + for await covers the same ground with less machinery.

Why does nothing happen until you subscribe, and why do publishers need to be stored?

Combine publishers are cold: they're a description of work, not the work. sink/assign is what starts it, and the returned AnyCancellable owns the subscription — drop it and the stream is cancelled immediately. That's why “my publisher never fires” is nearly always a cancellable that went out of scope, and why you keep a Set<AnyCancellable>.

Why is debounce the operator interviewers ask about?

Because it demonstrates the point of the whole framework: a real product requirement (“don't hit the API on every keystroke”) expressed declaratively, with the timer, the cancellation and the thread hop handled for you. Paired with removeDuplicates and switchToLatest, it's the canonical search pipeline — and the imperative version is 40 lines with a bug in it.

Where does Combine bite you in production?

Two places. Retain cycles: a sink capturing self strongly while self holds the cancellable is a cycle — hence [weak self] in sinks. And error termination: a failure completes the publisher permanently, so a search stream that errors once goes silent forever. You need catch/retry/replaceError to keep the pipeline alive — the debugging experience for that is a genuine argument for async/await.

7. Networking & Security

● Q7.1 — URLSession & Codable

 
struct User: Codable { let id: Int; let name: String }

func fetch() async throws -> User {
    let (data, response) = try await URLSession.shared.data(from: url)
    guard (response as? HTTPURLResponse)?.statusCode == 200 else {
        throw URLError(.badServerResponse)
    }
    return try JSONDecoder().decode(User.self, from: data)
}

CodingKeys maps a differently-named key. keyDecodingStrategy = .convertFromSnakeCase for snake_case APIs.

Go deeper

Why wrap URLSession in your own client instead of calling it directly?

Because the call site shouldn't know about headers, base URLs, auth refresh, retry, or decoding. A thin client gives you one place to add a token, log a request, or switch to a mock — and it gives your view models a protocol to test against instead of the network.

The anti-pattern is not “using URLSession”, it's spreading URL construction and decoding across 40 files so that changing an endpoint means 40 edits.

Why does everyone use Codable instead of parsing JSON by hand?

Because hand-parsing is where the bugs live: a typo in a key, a missed nil check, a type assumed to be Int that arrives as String. Codable makes the model the schema, fails loudly with a typed DecodingError that names the key path, and costs no runtime reflection because the compiler synthesizes the code.

Why is a decoding failure often better than a lenient fallback?

Because silently substituting a default hides a contract break: you ship a screen showing 0 instead of the real balance, and nobody notices for a week. A loud decode error at the boundary tells you the backend changed. Where resilience genuinely matters (a feed with one bad item), decode per element and skip the failures rather than making every field optional — blanket optionals push the problem into the UI layer.

Why is retry harder than it looks?

Because not every failure should be retried and not every request is safe to repeat. Retry on timeouts and 5xx, never on 4xx (you'll just fail faster); use exponential backoff with jitter so a server recovering from an outage doesn't get a synchronized stampede from every client; and only auto-retry idempotent requests — a repeated POST can charge a card twice.

● Q7.2 — Security (very common in fintech/banking)

Go deeper

Why Keychain and not UserDefaults — isn't the app sandbox already private?

UserDefaults is a plist in the app container: unencrypted, included in backups, and readable on a jailbroken or forensically-imaged device. Keychain is hardware-encrypted by the Secure Enclave, survives reinstall only if you want it to, and supports access policies — WhenUnlockedThisDeviceOnly means it can't even leave the device via backup.

Rule to say out loud: tokens, keys, PII → Keychain. Feature flags and “last tab selected” → UserDefaults.

Why is certificate pinning worth the operational pain?

It closes the one hole TLS leaves open: a trusted-but-wrong certificate — a corporate MITM proxy, a compromised CA, or a user tricked into installing a profile. Without pinning, anyone who can add a root CA to the device reads your traffic in plaintext.

The pain is real: pin the wrong thing and a certificate rotation bricks every installed app. That's why you pin the intermediate CA or the public key rather than the leaf, ship a backup pin, and keep a remote kill switch.

Why can't you rely on jailbreak detection or obfuscation as a security control?

Because they run on the attacker's device. Any check the client performs, the attacker can patch out — that's the whole premise of a compromised device. They're speed bumps that raise cost, not controls.

The security boundary has to be the server: validate entitlements, receipts, and limits server-side; treat the client as untrusted input. Say this in an interview and you sound like someone who's shipped a banking app.

Why is biometric auth not the same as authorization?

Face ID tells you the device owner is present; it doesn't prove anything to your backend. A local LAContext.evaluatePolicy returning true is a boolean an attacker with a patched binary can forge. Use biometrics to unlock a Keychain item (with .biometryCurrentSet, so re-enrolling a finger invalidates it) and let the released token be what authorizes the request — that's a cryptographic guarantee rather than a UI outcome.

⭐ The most important section for a senior role. Questions usually take the form: "Which architecture would you choose for project X? Why? Trade-offs?" — there's no "absolutely correct" answer; what matters is reasoning about the trade-offs.

● Q8.1 — MVC (Apple's) and its problems

 
      ┌──────────────┐
      │  Controller  │◄──► View
      │ (ViewController)
      └──────┬───────┘
             ▼
          Model

Problem: the view controller bloats (Massive View Controller) — it holds UI, business logic, networking, and data all at once. Hard to test, hard to maintain.

Go deeper

Why does MVC degrade into Massive View Controller? The pattern isn't wrong on paper.

Because on iOS the C and the V are fused: UIViewController owns the view lifecycle, so it's the natural place to put everything the view needs — and everything is a lot. There's no designated home for formatting, validation, navigation, or state, so they all land in the one class that has access to all of them.

The result isn't ugly code, it's untestable code: logic entangled with viewDidLoad and UIKit can't be exercised without a running view hierarchy.

Is MVC ever the right choice today?

Yes, and saying so is a maturity signal. For a screen that's mostly a static form, a settings list, or a one-off utility, MVC is the least ceremony that works, and adding a view model + coordinator + use case is three files to save nothing.

Choose architecture by how much logic the screen has and how long it will live, not by fashion.

Why does “move code out of the view controller” actually help — what do you gain concretely?

You gain a place to test. Once formatting and state transitions live in a plain type with no UIKit import, they can be tested in milliseconds without a simulator, they can be reused by a widget or a watch app, and they can be reasoned about by someone who has never opened the storyboard. That's the payoff — the file count going up is the price, not the benefit.

● Q8.2 — MVVM (the most popular today)

 
┌────────┐  binding   ┌────────────┐        ┌────────┐
│  View  │◄──────────►│  ViewModel │───────►│  Model │
│ (VC/SwiftUI)         │ (logic +   │        │ (data) │
└────────┘  (Combine/  │  state)    │        └────────┘
            @Published) └────────────┘
  • ViewModel holds presentation logic + state, does not import UIKit → testable.
  • Binding via Combine (@Published) or SwiftUI (@StateObject).
  • ViewModel is usually @MainActor (since it pushes state out to the UI).

Interview answer: "MVVM separates business/presentation logic from the view, making the ViewModel easy to unit test and the view thinner. Trade-off: can be over-engineering for a simple screen, and binding gets complex without framework support."

Go deeper

Why is MVVM the default on iOS today rather than MVP or plain MVC?

Because it matches how SwiftUI and Combine already work: the view model publishes state and the view renders it. There's no need for a presenter to imperatively poke the view — binding does it. So MVVM is the pattern with the least friction against the framework, which is the real reason it won.

It also gives you the testing seam you want: the view model is a plain type with no UIKit/SwiftUI import, so its logic is unit-testable without a view.

Why must the view model not import UIKit — what breaks if it does?

You lose the only thing MVVM bought you. Once the view model touches UIViewController or UIImage, tests need a simulator, the type can't be reused by a widget/watchOS target, and “business logic” and “presentation” have merged again — you've rebuilt the massive view controller with an extra file.

What is the failure mode of MVVM, and how do you avoid it?

The massive view model: networking, caching, mapping, validation and navigation all pile into one class of 800 lines, because “not in the view” isn't a design. The fix is naming the layers below it — repository for data access, use case / service for business rules, a router or coordinator for navigation — and letting the view model only orchestrate them into display state.

Where should navigation live, and why is that the hardest part?

Not in the view model, if you want it testable — a view model that calls present depends on UIKit again. Common answers: a Coordinator (UIKit), or a router/navigation-state enum driven by NavigationStack (SwiftUI). It's the hardest part because navigation is inherently about who owns the screen graph, which no single-screen pattern answers — say that explicitly and you'll sound senior.

● Q8.3 — MVP vs VIPER

MVP: View ↔ Presenter ↔ Model. The Presenter holds the logic, the View is passive (protocol). Similar to MVVM but usually without automatic data binding (explicit method calls).

VIPER: View · Interactor · Presenter · Entity · Router.

              │
            Router (navigation)
  • Very fine-grained separation, ~5 files per module → good for large teams, long-lived projects, many standardized screens.
  • Trade-off: lots of boilerplate, overkill for a small app.

Go deeper

Why would anyone choose VIPER given how much boilerplate it costs?

For one reason: large teams on a long-lived app. When five squads ship into one codebase, having a rigid, identical shape per screen means merge conflicts are rare, ownership is obvious, and a new hire can navigate an unfamiliar module immediately. The boilerplate buys predictability, and at that scale predictability is worth more than brevity.

Why is VIPER usually the wrong choice for a small team?

Because you pay the cost on every screen and only collect the benefit at scale. Five files and three protocols for a settings toggle means slower feature work, more indirection when debugging, and pressure to “just put it in the presenter” — which erodes the discipline that was the whole point. If you can't state which problem the extra layers solve for your team, they're overhead.

What does MVP still offer that MVVM doesn't?

Explicitness. The presenter calls the view through a protocol, so the flow is easy to read and step through in a debugger — there's no implicit reactive graph deciding when the UI updates. That makes MVP a reasonable fit for imperative UIKit code, and for teams who find binding-heavy code hard to reason about. Its downside is exactly that manual wiring: more code, and no free diffing.

How do you actually answer “which architecture would you use?” in an interview?

Don't name a favourite; name the criteria. Screen complexity, team size, expected lifetime, testing requirements, and whether the UI is SwiftUI or UIKit. Then commit: “SwiftUI product, small team, high test coverage → MVVM with a repository layer; I'd only reach for something heavier if we had many squads sharing modules.” Interviewers are testing whether you choose deliberately, not whether you like TCA.

● Q8.4 — Clean Architecture (a staple senior question)

Principle: dependencies only point inward. Inner layers don't know about outer layers. Business logic (Domain) is independent of frameworks/UI/DB.

Go deeper

Why must dependencies point inward? What concretely goes wrong if the domain imports the network layer?

You lose the ability to change the outside without touching the inside. If the domain imports URLSession or Core Data, then swapping REST for GraphQL, or Core Data for SwiftData, means editing business rules — and testing a rule requires standing up a database.

Pointing inward means the domain declares a protocol it needs and the outer layer implements it. That single inversion is what makes the core independently testable and independently reusable.

Isn't this just more files for the same behaviour? What's the return on that cost?

The return is measured in change cost, not line count. Business rules become testable in milliseconds with no simulator; a backend migration touches one layer; the same domain powers app, widget, and watch targets; and “where does this rule live?” has one answer, so features stop leaking into view controllers.

If the app is small and short-lived, that return never arrives — which is why Clean Architecture on a 6-screen app is a legitimate criticism, and saying so shows judgment.

Why are separate DTO and domain models worth the mapping code?

Because it stops the backend's shape from dictating your app's shape. Without mapping, a renamed JSON field ripples into your views, every field the API leaves optional makes your domain optional, and dates arrive as strings everywhere. With a boundary you validate and normalize once — the domain model can be non-optional and correct-by-construction, which removes a pile of defensive code from the UI.

How do you decide how many layers to actually use?

Add a layer when you can name the change it protects you from. Two backends or a planned migration → repository. Complex rules reused by several screens → use cases. Neither → don't. The senior move is a pragmatic subset: domain models + repository protocol + a couple of use cases where logic is genuinely shared, and no ceremony where a screen is just displaying a list.

● Q8.5 — TCA (The Composable Architecture)

A unidirectional data flow architecture (like Redux) from Point-Free, popular in the modern SwiftUI community.

        ┌──────────── Action ────────────┐
        │                                 │
     ┌──▼───┐   Reducer(State, Action)  ┌─┴─────┐
     │ View │◄──────── State ───────────│ Store │
     └──────┘   (single source of truth)└───┬───┘
                                            │ Effect (async)
                                            ▼
                                        Environment (deps)

Components: - State: value type, single source of truth. - Action: an enum of every event (user tap, response arriving...). - Reducer: (inout State, Action) -> Effect — pure, mutates state, returns an effect. - Store: holds the state, receives actions, runs the reducer. - Effect: an async side effect (network...) → returns a new Action. - Dependency: injected via environment → extremely testable (easy to swap dependencies).

Pros: absolutely test-friendly, predictable state, composes modules well. Cons: steep learning curve, boilerplate, depends on a third-party library, has overhead.

Quick comparison for interviews:

Architecture Testability Boilerplate Fits
MVC Low Low Prototype, very small app
MVVM Medium–high Medium Most apps (a safe default)
VIPER High Very high Large team, standardized modules
Clean High High Large app, many data sources, long-lived
TCA Very high High Pure SwiftUI, FP-minded team, needs predictable state

Go deeper

Why adopt TCA when MVVM already works?

For three guarantees MVVM doesn't give you: one way to change state (send an action to a reducer), exhaustive testability of state transitions including effects, and composition — small features combine into a parent without ad-hoc glue. State becomes a value you can snapshot, replay and diff, which is why time-travel debugging is possible at all.

The teams that benefit most have many contributors and complex flows where “who mutated this?” is a real question.

What does TCA cost, honestly?

A steep learning curve, heavy generics (and the compile times and error messages that come with them), a third-party dependency at the core of your app, and real ceremony for simple screens. Its exhaustive test store is a strength that also makes tests brittle when state grows.

Naming these costs unprompted is what separates “I read a blog post” from “I shipped it”.

Why must the reducer be a pure function, and where does the side effect go?

Purity is what makes the transition testable: same state + same action ⇒ same next state, with no clock, network or randomness involved. So anything impure is returned as an Effect and executed by the store, with dependencies injected — which is why in tests you can substitute a clock and a fake API and assert the exact action sequence.

When would you say no to TCA in an interview?

Small team, small app, tight deadline, or a team without Swift generics depth — the ramp-up cost dominates. Also when you can't accept a large external dependency shaping your whole codebase. The framing to use: “I'd adopt it for a complex, long-lived, multi-team product; for a 10-screen app I'd take @Observable MVVM and spend the time on tests.”

● Q8.6 — Dependency Injection

 
// Constructor injection (the most favored — clear, easy to test)
final class ProfileViewModel {
    private let repo: ProfileRepository
    init(repo: ProfileRepository) { self.repo = repo }
}

// Test: inject a mock
let vm = ProfileViewModel(repo: MockProfileRepository())

Kinds: constructor (best), property, method. Avoid a global singleton (hard to test, hidden dependency). A DI container (Swinject/Factory) for larger projects.

Go deeper

Why is DI worth doing at all — what problem does it solve?

It makes dependencies visible and replaceable. A type that constructs its own URLSession or reads a singleton has a hidden dependency: you can't test it without the network, and you can't tell from the signature what it touches. Injecting turns that into part of the contract.

The payoff is not abstraction for its own sake — it's that tests become fast and deterministic, and swapping an implementation (mock, staging, feature flag) stops being a code edit.

Why are singletons criticised when they're so convenient?

Because they're global mutable state with a nice name. Three consequences: hidden coupling (the signature doesn't say the type uses it), test pollution (state leaks between tests, so order matters), and lifetime you don't control (it lives for the app's life, whether you want it to or not).

They're acceptable for genuinely process-wide, stateless things — a logger, a keychain wrapper — behind a protocol so tests can substitute them.

Why prefer constructor injection over a container or a property?

Because the compiler enforces it. A missing constructor dependency doesn't build; a missing container registration crashes at runtime, often in a rarely-hit screen. Constructor injection also documents the dependency count — when the initialiser has nine parameters, the type is doing too much, and that's useful pain.

Use a container when the graph is genuinely large; use property injection only where the framework forces it (storyboard-instantiated controllers).

When does DI become over-engineering?

When you write a protocol with exactly one implementation and no test that uses a second one. That's indirection with no payoff: two files, one jump-to-definition detour, zero flexibility gained. The test to apply: is there a second implementation — a mock counts — that you actually use? If not, inject the concrete type and add the protocol the day you need it.

Go deeper

Why test at all when QA will click through the app anyway?

Because manual testing doesn't scale with regression surface. Tests are how you find out that a change to the discount rule broke checkout before shipping, and how a refactor becomes safe rather than scary. The real deliverable isn't coverage — it's the ability to change code confidently.

Why do we need test doubles instead of hitting the real API?

Because a test that touches the network is slow, flaky, and untargeted: it fails when the wifi hiccups and it can't reproduce a 500 or a timeout on demand. A stub makes tests deterministic and lets you assert the interesting paths — empty list, malformed payload, expired token — which are exactly the cases real APIs won't produce on command.

Why distinguish mock from stub? Isn't it pedantry?

It's a distinction about what you assert. A stub feeds state in — “given the API returns 3 items, the view model shows 3 rows”. A mock asserts an interaction — “logout() was called exactly once”. Mixing them up produces tests that assert implementation details, so every refactor turns red even though behaviour is unchanged. Prefer stubs and state assertions; use mocks where the interaction is the requirement (analytics fired, payment charged once).

What makes a test suite worth keeping, rather than a maintenance tax?

Test behaviour, not implementation; keep them fast and independent (no shared mutable state, no order dependence); prioritise where bugs are expensive — business rules, money, state machines, mappers — over trivial getters. And treat a flaky test as a broken test: a suite people learn to ignore is worse than none, because it costs time and buys no confidence.

Cache strategy: cache-first (show local immediately, refresh in the background) vs network-first. Invalidation via TTL / ETag / push notification. Discuss conflict resolution during sync.

Go deeper

Why offline-first rather than just adding a cache when someone complains?

Because it changes the source of truth. Cache-as-an-afterthought means the UI depends on the network and shows spinners and errors; offline-first means the UI always reads local storage and the network's only job is to keep that store fresh. The result is instant launches, a usable app on the subway, and one code path instead of two.

Retrofitting this later is expensive, which is why it's an architecture decision rather than an optimization.

Why is “last write wins” usually the wrong conflict policy — and when is it fine?

Because it silently destroys user data: two devices edit the same note and one edit vanishes with no trace. It's fine for state that's genuinely disposable or single-owner — a read flag, a UI preference, a cached counter.

Anything the user authored deserves better: per-field merge, a server-side version/ETag with a rejected write, or an explicit conflict UI. Choosing consciously and saying why is the answer interviewers want.

Why does an outbox queue matter more than retrying the request?

Because a retry loop lives in memory: kill the app and the user's action is gone, even though the UI said “saved”. Persisting the intent means the mutation survives relaunch, can be retried with backoff, and can be shown in the UI as pending.

The catch is idempotency: replaying a queued POST after an ambiguous timeout can duplicate it, so each mutation needs a client-generated id the server dedupes on.

How do you decide between URLCache, files, and a database?

By query shape and lifetime. URLCache for plain HTTP GET response reuse — nearly free, honours cache headers, no schema. Files for large blobs (images, video, PDFs), because they don't belong in a database and you want the OS to evict them. SQLite/Core Data/SwiftData when you need to query, sort, page, or relate records — and when the data must be the app's source of truth, not just a copy of a response.

  • Design image loading + caching (like SDWebImage): memory cache (NSCache) + disk cache + cancellation on cell reuse.
  • Design pagination for a feed (cursor vs offset, prefetch).
  • Design real-time chat (WebSocket, message status enum, sending images via HTTP + URL over the socket, offline queue).

Go deeper

What are interviewers actually scoring in an iOS system-design round?

Not the diagram. They're scoring whether you clarify requirements before designing, whether you name trade-offs instead of picking a favourite tool, whether you think about failure (offline, retries, partial data), and whether you consider the things only mobile has: battery, cellular data, background execution limits, app size, and OS version spread.

What's the structure to use so you don't ramble?

Five steps, out loud: 1) clarify scope and constraints (users, offline?, real-time?, OS floor); 2) sketch the layers (UI → domain → data → transport); 3) pick storage and sync strategy with a reason; 4) walk one critical flow end to end including its failure modes; 5) state what you'd measure and what you'd cut for v1. Announcing the structure first buys you credit immediately.

What's the most common mistake candidates make here?

Designing the perfect system instead of the right one: microservice-shaped layers for a 5-screen app, or naming a library instead of a strategy. The second most common is ignoring the mobile-specific constraints — a design that assumes reliable network and unlimited background time is a web design wearing an iOS badge.

How do you handle a requirement you don't know how to build?

Say so, then reason from principles: what are the primitives (background tasks, push, streaming, on-device ML), what's the simplest thing that could work, and what would you prototype to reduce the risk. Interviewers rate how you approach unknowns far higher than a memorised answer — a confident wrong certainty scores worse than a structured “here's how I'd find out”.

12. AI-Assisted Development (Workflow using AI)

This section is for the "AI-First iOS Developer" role — companies want to know how you use AI (ChatGPT/Claude/Copilot/Cursor) in your daily workflow without trading off quality. Your answer should make the boundary clear: where AI speeds things up, and where a human is still accountable.

● Q13.1 — How do you use AI in your workflow without trading off quality?

Core: AI is a productivity accelerator, not a replacement for engineering judgment. Treat every AI output as a first draft — always run it through review, tests, and hold it to the same quality bar as human-written code.

Go deeper

Why do teams get slower with AI instead of faster?

Because generation is the cheap part and review is the bottleneck. If you accept a 400-line diff you didn't read, you've moved the cost from writing to debugging — and debugging code nobody understands is the most expensive mode there is.

The teams that get faster keep the diffs small, keep a human accountable per PR, and use AI where verification is cheap: tests, boilerplate, migrations, code you can run immediately.

Where is AI genuinely high-leverage on an iOS codebase, and where is it not?

High: test scaffolding, Codable models from a JSON sample, mechanical refactors, migrating callbacks to async/await, writing the first draft of documentation, explaining unfamiliar code. All verifiable in seconds.

Low or negative: concurrency and memory-ownership decisions, security-sensitive code, anything depending on a very recent API (training lag means confident-but-obsolete answers), and architecture choices that depend on team context the model can't see.

Why is “I always review AI output” not a sufficient answer in an interview?

Because it's unfalsifiable. What earns credit is a process: small scoped prompts, the diff must compile and pass tests locally, security-relevant code gets a second reviewer, no generated dependency without a licence check, and CI is the gate rather than trust. Naming the gate matters more than professing diligence.

How do you keep ownership of the code when AI wrote it?

By the rule that the person who merges is the author. Practically: read every line before committing, rewrite anything you can't explain, don't let the model choose your architecture, and keep the change small enough that reading it is realistic. If you can't defend a line in review, it doesn't ship — that's the whole discipline.

● Q13.2 — How do you write a good system prompt for Swift/iOS?

Core: A good prompt is a mini technical spec: role, platform/version, required architecture, coding constraints, and the desired output format. The more specific, the less the AI hallucinates.

"Act as a Senior iOS Architect. Target iOS 18+, Swift 6, SwiftUI, MVVM + Clean Architecture, async/await, protocol-based DI.
Constraints: no force unwraps, no Massive ViewModel, no singleton service, business logic must live in the UseCase layer.
Output: code + trade-off explanation + unit tests using a mock repository."

Common trap: a vague prompt ("write me a login screen") → the AI picks its own architecture, often stuffing networking code straight into the View. Always state the layer boundaries explicitly in the prompt — don't let the AI guess.

Go deeper

Why does a system prompt matter more than a clever question?

Because it removes ambiguity the model would otherwise fill in with defaults from its training data — usually older Swift, UIKit patterns, and a random third-party library. Pinning the context (Swift version, minimum iOS, architecture, SwiftUI vs UIKit, concurrency style) changes the output more than rephrasing the request ever will.

What actually belongs in it, concretely?

Constraints the model cannot guess: language and platform versions; “use async/await, not GCD”; “no third-party dependencies”; the architecture and layer boundaries; the error-handling convention; whether tests are required; and the house style. Plus what not to do — “don't invent APIs, say you're unsure instead” is worth several paragraphs of politeness.

Why ask for an explanation or a plan before the code?

Because it makes the model's assumptions inspectable before you have 300 lines to review, and a wrong assumption is cheap to correct at plan stage. It also reduces the confident-nonsense failure mode: a model that has to justify a choice is less likely to hallucinate an API that would make the justification collapse.

How do you stop it inventing APIs that don't exist?

Ground it: paste the real signatures, the actual header, or the file it must modify, and tell it to prefer them over recall. Then say explicitly “if an API may not exist, flag it rather than guessing”. And verify mechanically — it compiles or it doesn't. Hallucinated APIs are the one failure mode Xcode catches for free, so lean on the compiler rather than on trust.

● Q13.3 — How does reviewing an AI-generated PR differ from a human-written one? (a staple question)

Core: AI code usually compiles and "looks correct" but can get the architecture wrong, miss edge cases, or violate thread-safety without any clear error. Reviewing an AI PR needs to be stricter, focused on what the compiler can't catch.

// ❌ What AI commonly generates: shared state with no isolation → latent data race
final class ChatStore {
    var messages: [Message] = []   // multiple Tasks writing at once → race condition
}

// ✅ After review: isolated with an actor
actor ChatStore {
    private(set) var messages: [Message] = []
    func append(_ m: Message) { messages.append(m) }
}

Checklist for reviewing an AI PR:

  • Actor isolation / cancellation: is a Task cancelled at the right time (onDisappear, deinit)?
  • Is any networking/business logic stuffed straight into the View/ViewModel, breaking the architecture boundary?
  • Does error handling carelessly "swallow" errors with try??
  • Retry/timeout for async calls — AI often forgets fail/cancel/empty cases.
  • Does the naming/style match the rest of the codebase, or does it show sloppy "AI-generated" tells?

Go deeper

Why does AI code need a different review lens at all?

Because the failure distribution is different. A human writes code that reflects a mental model — wrong sometimes, but consistent. A model writes code that is locally plausible everywhere: syntax is clean, naming is tidy, and the bug is a subtly wrong assumption rather than a sloppy line. Reviewers trained on human mistakes read the surface, and the surface is exactly what AI gets right.

So what do you look for first?

Assumptions rather than style: does it handle empty/nil/error paths or only the happy path? Are the APIs real and current? Is the concurrency and ownership actually correct (@MainActor, Sendable, weak) or just plausible? Does it duplicate something the codebase already has? And do the tests assert behaviour, or do they assert whatever the implementation happens to do?

Why is “it passes the tests” weaker evidence when the AI wrote the tests too?

Because the tests then encode the same misunderstanding as the code — they're a mirror, not a check. Green means self-consistent, not correct. That's why generated tests need a human to verify they test the requirement, and why at least one assertion should come from the spec rather than from reading the implementation.

What do you do about a 900-line generated PR?

Send it back. A diff too large to read is unreviewable regardless of who wrote it, and “AI wrote it” is not a reason to lower the bar — if anything the bar goes up, because nobody holds a mental model of it. Ask for it split by concern, each part compiling and tested on its own.

● Q13.4 — When should you absolutely not trust AI code blindly?

Core: High business/security-risk areas — AI can produce an implementation that "looks reasonable" but isn't safe.

  • Authentication / token storage — always personally verify the Keychain flow, don't copy the AI's implementation as-is.
  • Payment / finance — mistakes can cause double-charging, needs a self-designed idempotency key.
  • Encryption — AI may pick a weak algorithm/mode (e.g. ECB) without warning.
  • Concurrency-heavy code — AI often misses subtle race conditions between 2 await points.

Interview answer: "I once rejected AI-generated code because it stored shared mutable state with no actor isolation — I replaced it with an actor-based store before merging."

Go deeper

Which categories do you never take on trust, and why those?

Security and crypto (a plausible-looking implementation can be catastrophically weak, and it won't fail a test), money and billing (rounding, currency, idempotency — errors are irreversible), concurrency (races pass tests and fail on users' devices), data migrations (one wrong mapping and user data is gone), and anything depending on a very recent API (training lag produces confident, obsolete code).

The common thread: failures that tests don't catch and users can't recover from.

Why is confident-sounding wrongness the real hazard rather than obvious errors?

Because obvious errors get caught. A model has no calibrated uncertainty in its prose — it explains a hallucinated API with exactly the tone it uses for a correct one, so the usual human signal (“they sound unsure, let me check”) is absent. That inverts review instincts, which is why grounding in real signatures and compiling early matter more than reading the explanation.

How do you talk about this in an interview without sounding anti-AI?

Frame it as calibration, not refusal: “I use it heavily where verification is cheap, and I slow down where a failure is silent and expensive.” Then give the mechanism — compiler and CI as the gate, second reviewer on security, no generated migration without a dry run on a copy of real data. That reads as someone who ships with AI, not someone who fears it.

● Q14.1 — What is Apple Intelligence? On-device + Private Cloud Compute architecture

Go deeper

Why did Apple build Private Cloud Compute instead of just running everything on-device or using a normal server?

Because neither extreme works. On-device models are small — they can't do everything — and a conventional cloud means your data sits on a server that operators can access. PCC is the middle: server-class models on Apple silicon with no persistent storage of your request, no operator access, and independently inspectable server images.

The privacy claim is the product here, which is why it's worth being able to describe: cryptographic attestation of the software image, not a promise in a policy document.

Why does the on-device/PCC split matter to you as an app developer?

Because it determines what you can rely on. On-device: free, offline, private, low latency, but a small model with a limited context window and quality that varies. PCC: much more capable, needs connectivity, and is routed by the system rather than by you. Your design has to degrade gracefully — feature availability varies by device, region, language, and user settings.

What does the device capability spread mean for shipping a feature on top of it?

That “Apple Intelligence” is not a guaranteed platform capability. It requires supported hardware, a supported language, and the user having it enabled — so any feature built on it needs a fallback path, a capability check at runtime, and honest UI when unavailable. Designing as if it's always present is the mistake interviewers listen for.

● Q14.2 — Foundation Models framework: LanguageModelSession & Structured Output

Core: The FoundationModels framework (introduced at WWDC 2025) lets an app call Apple's on-device generative model directly, with no backend needed — LanguageModelSession is the API that manages a single conversation session, and the @Generable macro lets the model return structured output (a real Swift type) instead of free-form text you'd have to parse yourself.

import FoundationModels

@Generable
struct MeetingSummary {
    @Guide(description: "3 bullet points summarizing the meeting")
    var highlights: [String]
    @Guide(description: "List of action items with the owner for each")
    var actionItems: [String]
}

let session = LanguageModelSession()   // keeps conversation context — no need to manage history yourself
let result = try await session.respond(
    to: transcript,
    generating: MeetingSummary.self          // forces the model to return the exact schema, no manual JSON parsing
)
print(result.content.actionItems)

Note on a common terminology mistake: many prep materials loosely call this a "Prompt Session" — the official API name is LanguageModelSession, and structured output is declared with the @Generable + @Guide macros, not by asking the model to "return JSON" in the prompt text.

Go deeper

Why use the on-device Foundation Models framework instead of calling a cloud API?

Four reasons that don't apply to a cloud call: no per-token cost, works offline, data never leaves the device (which can turn a compliance conversation into a non-issue), and no key management. Latency is also predictable — no network variance.

The trade is capability: a small model, a limited context window, and no control over which model version you get.

Why does structured output (@Generable) matter so much more than prompting for JSON?

Because parsing free-form text is where LLM features break: a stray sentence before the JSON, a trailing comma, a hallucinated field, and your decode fails on a user's device. Guided generation constrains decoding to your schema, so you get a typed Swift value rather than a string you have to defend against.

It also removes a whole prompt-engineering ritual (“respond with only valid JSON, no markdown”) that never worked reliably anyway.

Why keep a session alive rather than making one call per request?

Because the session holds the conversation context, so follow-ups work without you re-sending the history — and re-sending costs both time and context window. The counterpoint is that a session grows: eventually you must trim or summarize older turns, or you'll exceed the window and start failing in exactly the sessions your most engaged users have.

What failure modes must you handle when shipping this?

Availability (unsupported device, language, or Apple Intelligence disabled — check before showing the entry point), guardrail refusals (the model declines; handle it as a normal state, not an error dialog), context-window overflow on long sessions, and quality variance. And latency: even on-device, generation is slow enough that you need streaming or a visible progress state.

● Q14.3 — Tool Calling in Foundation Models

Core: Conform to the Tool protocol so the model can decide on its own when it needs to call a real Swift function (e.g. get the weather, look up app data) instead of only generating text — similar to the function-calling concept in OpenAI/Anthropic but running entirely on-device.

struct WeatherTool: Tool {
    let name = "getWeather"
    let description = "Gets the current weather for a city"

    @Generable
    struct Arguments { @Guide(description: "City name") var city: String }

    func call(arguments: Arguments) async throws -> ToolOutput {
        let w = try await weatherService.fetch(city: arguments.city)
        return ToolOutput("\(w.temperature)°C, \(w.condition)")
    }
}

let session = LanguageModelSession(tools: [WeatherTool()])  // the model decides on its own when to call the tool

Security trap: a tool should never have more permission than it needs (least privilege) — e.g. a tool that reads the calendar shouldn't be able to delete events unless explicitly granted that permission.

Go deeper

Why does a model need tools at all — can't it just answer?

Because a language model knows its training data, not your data or the current state of the world. Tools are how it reaches the user's calendar, your database, today's price, or the device's location. Without them, an assistant can only talk about things; with them it can act on them.

What makes a tool definition good or bad, and why does it matter so much?

The description is the interface — the model decides whether and how to call based on it. Vague names, overlapping tools, or unexplained parameters produce wrong calls and loops. Good practice: one clear job per tool, explicit parameter meanings and units, narrow types (enums, not free strings), and a documented failure result so the model knows what “not found” looks like.

Why must tool results be treated as untrusted input?

Because whatever the tool returns lands in the model's context and can steer the next step. If a tool fetches a web page, an email, or user-generated content, that text can contain instructions — and a model that can also call a destructive tool may follow them. This is indirect prompt injection, and the mitigation is on your side: least-privilege tools, no irreversible action without confirmation, and never letting tool output be interpreted as policy.

Why is “tool calling” different from just letting the model generate code to run?

Because a tool is a bounded capability with a typed signature that you implemented and can audit; generated code is arbitrary execution. Tools give you a whitelist and a place to enforce permissions, rate limits and validation. The design goal is that even a completely misled model can only do things from a list you're comfortable with.

What's the decision rule, stated crisply?

On-device when the task is bounded and the data is sensitive: classification, extraction, tagging, short summaries, rewriting, intent parsing — plus anything that must work offline or at zero marginal cost. Cloud when the task needs reasoning depth, long context, or a specific model: multi-step analysis, long documents, code generation, high-quality multilingual output.

Why is a hybrid usually the real answer, and how do you structure it?

Because most products have both kinds of task. Route by task, not by preference: run the cheap classification on-device, escalate to cloud only for the hard step. Keep a single provider-agnostic interface so the routing is one implementation detail, and treat on-device as the fallback when the network fails.

That also gives you a cost lever you can pull later without touching feature code.

Which cost is easiest to underestimate on each side?

Cloud: per-token cost at scale plus latency variance — a feature that's fine in testing gets expensive and slow when it's in a hot path for every user. On-device: quality variance and the capability matrix — device support, language support, user opt-out — plus battery and thermals if you run it aggressively. Both bite in production rather than in the demo.

How do you make this decision defensible in an interview?

Anchor it to requirements rather than technology: data sensitivity, offline requirement, expected quality bar, latency budget, unit economics at your MAU, and the OS/device floor you support. Then commit to a routing rule and name what you'd measure to revisit it. “It depends” only scores if you say on what.

● Q15.1 — What is MCP? How is it different from REST?

Core: Model Context Protocol (MCP) is an open protocol standardizing how AI models communicate with external tools/data sources — a familiar analogy: "USB-C for AI". REST exposes an API for a developer to call; MCP exposes a "tool" with a description so the model itself discovers and decides whether to call it.

REST (developer-centric)          MCP (AI-centric)
GET /weather?city=Tokyo           Tool: GetWeather(city) — the model reads the description itself,
→ developer code knows in advance   decides on its own whether to call it, runtime tool discovery
  which endpoint to call

Go deeper

Why invent MCP when we already have REST and OpenAPI?

Because the consumer changed. REST is designed for a programmer who reads docs and writes the call; MCP is designed for a model that must discover capabilities at runtime and decide which to use. So the protocol carries self-describing tools, resources and prompts, plus a session and a standard transport.

The practical payoff is N×M collapse: any MCP-speaking client can use any MCP server, instead of every app writing a bespoke integration per tool.

What does MCP actually give you that a hand-rolled tool layer doesn't?

Discovery (tools/list, so capabilities can change without shipping an app update), a uniform schema for arguments and results, a session with lifecycle and negotiated capabilities, and an ecosystem of servers you didn't write. If your app has exactly three fixed tools, hand-rolling is fine — MCP earns its keep when the tool set is open-ended or shared across clients.

Where does MCP not fit?

Plain data fetching where you know the endpoint — a REST GET is simpler, cacheable and cheaper. Also high-throughput or latency-critical paths, and anything where you don't want the model choosing the call at all. Being able to say “I'd use REST here” is what stops this sounding like hype.

● Q15.2 — Architecting a secure MCP client in an iOS app (a staple question)

Core: The app should never hold credentials/API keys or call an MCP server directly — always go through a backend, since the app can be reverse-engineered. Apply Clean Architecture just like Q8.4: the domain defines the protocol, the transport layer is an implementation detail in the Data layer.

Swift App (View → ViewModel)
      │  calls through the MCPRepository protocol (Domain)
      ▼
Backend (holds OAuth token, rate limiting, logging)
      │
      ▼
MCP Server ──► Tools (Calendar, GitHub, DB, Slack...)

protocol MCPRepository {                       // Domain layer — doesn't know the real transport
    func invoke(tool: String, args: [String: Sendable]) async throws -> ToolResult
}

final class BackendMCPRepository: MCPRepository {      // Data layer — HTTP to the backend, NOT directly to the MCP server
    private let client: APIClient
    func invoke(tool: String, args: [String: Sendable]) async throws -> ToolResult {
        try await client.post("/mcp/invoke", body: ["tool": tool, "args": args])
    }
}

Interview answer: "I put the MCP transport in the Data layer behind a protocol in the Domain, exactly like how I separate the Repository in Clean Architecture — that way switching from a REST backend to a real MCP server (once Apple/the team supports it) doesn't touch the ViewModel."

Go deeper

Why shouldn't the iOS app talk to MCP servers and model providers directly?

Because anything in the app binary is readable — an API key in an iOS app is a published API key. Putting a backend in front gives you one place to hold secrets, enforce per-user rate limits and quotas, audit what was called, and change providers or tool policy without an App Store release.

That last point is the one people forget: a client-side security decision takes days to fix, a server-side one takes minutes.

Why is least privilege the central design rule here rather than an afterthought?

Because the model is a component you can't fully constrain by testing. Assume it will, at some point, be persuaded to attempt the worst call available to it. The only robust control is that the worst available call isn't very bad: read-only tools by default, scoped to the current user, with destructive operations either absent or gated behind explicit user confirmation.

What do you actually put in the transcript, and why does that matter?

Log every tool invocation with arguments, result status, user id and timestamp — but never the secrets or the full sensitive payload. It matters for two reasons: it's how you detect abuse and injection attempts, and it's how you answer “what did the assistant do to this account?” — which you will be asked after the first incident.

How do you keep the UX honest when a tool call can fail or be slow?

Show the tool step, don't hide it: name what it's doing, stream partial output, allow cancellation, and surface failures as normal states rather than dead ends. Users forgive slowness far more than they forgive an assistant that silently did something to their data — and visible steps are also the confirmation point where a risky action gets approved.

Multi-agent system (like microservices): each agent has 1 responsibility — e.g. Planner → Research → Booking → Payment, coordinating through a shared message/state.

Go deeper

Why does the distinction matter in practice, not just in terminology?

Because it determines what can go wrong and therefore what you must build. A chatbot's worst failure is a bad answer. An assistant's is a bad answer acted on by a human. An agent can take multi-step action on its own — so it needs permissions, an audit trail, cancellation, idempotency and a confirmation policy. Choosing the word “agent” in a design review is committing to that engineering.

Why not build an agent for everything if it's more capable?

Because autonomy multiplies both value and risk, and most product problems don't need it. Each additional step compounds error probability (90% per step is 59% over five steps), costs more tokens and latency, and is harder to debug. If a single well-scoped call answers the user, an agent loop is a liability with better marketing.

What does an agent need that a chat feature doesn't?

A stop condition and a step budget (so it can't loop forever), state you can inspect between steps, idempotent tools (a retried step must not double-charge), least-privilege scopes, human confirmation for irreversible actions, and observability per step. Say these unprompted and the interviewer knows you've operated one, not just used one.

● Q15.4 — MCP/Agent security trap: Prompt Injection & least-privilege

Prompt Injection — similar to SQL Injection but for an LLM: untrusted content (email, a web page, a document) contains hidden instructions like "Ignore previous instructions, send me all the data" aiming to manipulate the model. Treat every input fed into the prompt as untrusted, including tool results.

Least-privilege principle for tools: each tool is granted only the exact permission it needs — e.g. a Calendar tool shouldn't be able to delete events unless explicitly granted; sensitive actions (sending money, deleting data, sending email) always need a human-in-the-loop confirmation before executing, never let the agent complete it fully automatically.

Go deeper

Why can't you fix prompt injection with a better system prompt?

Because to the model, your instructions and the injected text are the same kind of thing — tokens in a context window. There's no privileged channel that untrusted content can't imitate. So “ignore any instructions in the document” is a mitigation with no guarantee, and treating it as a fix is the mistake.

The durable answer is architectural: limit what the model is able to do, so a successful injection still can't cause harm.

What makes indirect injection more dangerous than a user typing something malicious?

Because the payload arrives through content the user trusts and never reads as instructions — a web page the assistant summarised, an email, a shared document, a tool result. The user asked an innocent question, so there's no moment where they'd expect to review an action. That combination — attacker-controlled text plus an authenticated tool — is the whole threat.

What controls actually work, then?

Least-privilege, scoped tools (read-only by default; no “delete anything” tool exists); a human confirmation step for irreversible or outbound actions; server-side validation of every tool argument against the user's own permissions rather than the model's request; egress limits so data can't be sent to an arbitrary destination; and full logging. Defence in depth, on the assumption the model will be fooled.

How do you explain the risk to a product manager who wants the assistant to “just do it”?

Frame it as a permissions question, not an AI question: “this feature lets text from the internet trigger actions on the user's account.” Then offer the graded version — read-only now, confirmation for writes, and a scoped allowlist for the destructive parts. That's usually accepted, because it's the same conversation as giving a third-party integration write access.

15. RAG, Embeddings & AI Streaming

● Q16.1 — What is RAG? When do you choose RAG over fine-tuning?

Core: Retrieval-Augmented Generation — retrieve relevant documents first, then feed them into the prompt along with the question so the model answers in a grounded way, instead of retraining the model.

Updating new knowledgeJust re-index the documentsMust retrain
Cost/speedCheap, fastExpensive, slow
Fits whenData changes frequently (policy, catalog)Need to change the model's behavior/style, not just knowledge

Go deeper

Why is RAG the default answer instead of fine-tuning?

Because most “the model doesn't know our stuff” problems are knowledge problems, and RAG solves those directly: update the index and the answer changes immediately, no retraining, no dataset, and you can cite the source. Fine-tuning teaches behaviour and format, not facts — and baked-in facts go stale and can't be cited.

When is fine-tuning genuinely the right tool?

When you need a consistent style, a domain vocabulary, a rigid output format, or a smaller/cheaper model to perform like a bigger one on one narrow task. The tell is that you're fixing how it answers, not what it knows. In practice the answer is often both: fine-tune the form, retrieve the facts.

Why does RAG quality usually fail at retrieval rather than at generation?

Because the model can only work with what you hand it. If chunking split a table in half, if the embedding doesn't capture the domain's vocabulary, or if top-k returns three near-duplicates and misses the one relevant paragraph, no prompt fixes it. That's why evaluation has to measure retrieval separately — recall@k on real questions — before blaming the model.

What makes RAG hard to ship well, beyond the demo?

Chunking that respects document structure, keeping the index fresh as source data changes, handling “not in the corpus” without hallucinating, citation so users can verify, access control (retrieval must respect who is allowed to see what — a very common leak), and cost/latency of the extra hop. The demo is a weekend; the pipeline is the product.

● Q16.2 — Semantic search architecture: embeddings + vector DB + chunking

   ▼

Real-world ranking doesn't rely on vector similarity alone — it also factors in recency, permission, source trustworthiness (e.g. prioritizing the newest policy version). Choosing a vector DB (managed vs self-hosted) depends on scale, latency, and compliance requirements — there's no absolutely right choice.

Go deeper

Why embeddings instead of keyword search — and when is keyword still better?

Embeddings match meaning, so “how do I cancel my plan” finds a document titled “Ending your subscription”. Keyword search can't. But keyword search is still better for exact identifiers, product codes, names, and rare terms — where lexical precision beats semantic similarity. That's why serious systems use hybrid retrieval and rerank, not one or the other.

Why is chunking the highest-leverage decision in the whole pipeline?

Because the chunk is the unit of retrieval: it's what gets embedded, matched and handed to the model. Too small and you retrieve a sentence with no context; too large and the embedding averages several topics into mush and you burn context window. Respecting structure (headings, paragraphs, table integrity) with a modest overlap usually beats any amount of prompt tuning downstream.

Why does everyone use cosine similarity, and what does it miss?

Because it compares direction and ignores magnitude, which is what you want when comparing meaning across texts of different lengths. What it misses: similarity is not relevance. Two chunks can be near-identical in embedding space and only one answers the question — which is why you rerank, and why metadata filters (tenant, date, permission) must be applied at query time rather than hoped for.

On iOS specifically, when do you keep the index on-device versus server-side?

On-device when the corpus is the user's own data, when privacy is the selling point, or when it must work offline — a few thousand chunks in SQLite (or a vector extension) is very manageable. Server-side when the corpus is large, shared, updated centrally, or needs a heavier embedding model. The hybrid — on-device index of the user's data, server index of the shared corpus — is a strong answer because it maps to who owns the data.

● Q16.3 — Streaming AI tokens in SwiftUI with AsyncSequence (a staple question)

Core: Consume the stream with for await, update state on MainActor, keep a Task reference to cancel it at the right time — to avoid wasting tokens/cost when the user leaves the screen mid-stream.

@MainActor
final class ChatViewModel: ObservableObject {
    @Published var text = ""
    private var streamTask: Task<Void, Never>?

    func send(_ prompt: String) {
        streamTask?.cancel()                              // cancel the old stream if the user sends a new message
        streamTask = Task {
            text = ""
            do {
                for try await token in aiRepository.streamResponse(to: prompt) {
                    try Task.checkCancellation()              // re-check between tokens
                    text += token                                   // already on MainActor, UI update is safe
                }
            } catch { text = "Stopped." }
        }
    }

    func cancel() { streamTask?.cancel() }                       // call from .onDisappear
}

Trap: if streamResponse is not actor-isolated, appending directly to @Published var text from a background thread will crash/warn — always make sure the whole ViewModel is @MainActor as shown above.

Go deeper

Why stream at all instead of waiting for the full response?

Because the metric users feel is time to first token, not total time. A 6-second answer that starts appearing in 400ms feels responsive; the same answer delivered whole after 6 seconds feels broken. Streaming also lets the user stop early once they've seen enough, which saves tokens and their time.

Why AsyncSequence rather than a Combine publisher or a delegate?

Because it's a natural fit for “values over time, consumed in order, with backpressure and cancellation for free”. for try await reads like a loop, errors propagate with throws, and breaking out of the loop cancels the underlying task — the three things you'd otherwise hand-write with a publisher plus a cancellable plus manual teardown.

Why does naive per-token UI updating destroy performance, and what do you do instead?

Because every appended token triggers a SwiftUI state change and a re-layout of a growing text view — hundreds of layout passes per response, on the main thread. The fix is to decouple arrival rate from render rate: accumulate into a buffer and flush on a short interval (or every N tokens), so you render ~20 times a second instead of 300. That's the answer interviewers are listening for.

What else must the streaming UI handle to be production-quality?

Cancellation that actually stops the request (store the task; cancel on disappear and on a stop button), partial-response persistence so a killed app doesn't lose the message, error mid-stream (you already showed half an answer — don't replace it with an alert), auto-scroll that yields when the user scrolls up, and an explicit “generating” state so the send button can't fire twice.

● Q16.4 — Using an actor to protect conversation history from race conditions

Core: When multiple AI requests run concurrently (chat + document summary + image analysis at the same time), the conversation history is shared mutable state — use an actor to serialize access, combined with TaskGroup/cancellation so each request is independent and doesn't block the others.

actor ConversationStore {
    private var messages: [Message] = []

    func append(_ m: Message) { messages.append(m) }

    // trim context to reduce tokens: keep the most recent messages + a summary of the older ones
    func recentContext(limit: Int = 20) -> [Message] {
        Array(messages.suffix(limit))
    }
}

Reentrancy trap: between 2 await points in an actor method, another method can still slip in and mutate messages — if your logic depends on insertion order, always re-read the state right after each await instead of trusting a previously-read value (see also Q3.3).

Go deeper

Why does conversation history specifically need protection?

Because it's mutable state written from several directions at once: the user typing, a stream appending tokens, a tool result arriving, a cancellation trimming the last message, and persistence reading it. Interleave two of those without isolation and you get duplicated messages, lost turns, or a crash from a mutated array — and it reproduces once a week, on device only.

Why an actor rather than @MainActor on the whole view model?

@MainActor works and is often the simplest correct answer for small state. But history operations include non-UI work — token counting, trimming, summarising old turns, encoding for persistence — and doing that on the main actor competes with rendering while a response streams. A dedicated actor keeps that work off the main thread while still serialising access.

Where does actor reentrancy bite in this exact scenario?

Between the check and the write. `if !history.contains(id) { await save(); history.append(msg) }` — the await releases isolation, a second call runs the same check, and you append twice. Fix by not awaiting inside the critical section: compute outside, mutate in one uninterrupted step, or re-validate after the suspension.

Why is a token/context budget part of this design rather than an afterthought?

Because history grows without limit and the context window doesn't. If you don't decide the policy — drop oldest, summarise the middle, always keep the system prompt and the last N turns — the feature works in testing and fails for your heaviest users, which is the worst possible distribution. Owning that trimming rule inside the same actor keeps history and its budget consistent.

What's the first thing you decide, and why isn't it the UI?

Whether the app talks to the provider directly or through your backend — because that single choice determines key security, cost control, rate limiting, provider switching, and whether a policy change needs an App Store release. Get it wrong and every later decision inherits the mistake. Answer: your backend, unless the model is on-device.

Why is local persistence a core requirement rather than a nice-to-have?

Because a chat app is judged on “is my conversation still there?”. Streaming means a message can exist half-written when the app is killed; without local storage the user loses it and trust with it. Persisting per message (not per conversation) also gives you resume-after-crash, offline reading, and search.

How do you keep cost and latency under control in this design?

Trim the history you send (system prompt + last N turns, or summarise the middle) rather than resending everything; cache responses to identical prompts; pick the cheap model for cheap tasks (title generation, classification) and the strong one only for the main answer; stream so perceived latency stays low; and measure tokens per active user so a regression shows up before the invoice does.

What do candidates usually forget here?

The unglamorous parts: cancellation of an in-flight stream, retry with an idempotency key so a resend doesn't duplicate a message, moderation/abuse handling, the App Review requirement for user-generated-content moderation and reporting, per-user rate limits to stop one account burning your budget, and observability — TTFT, tokens, error rate per model. Those are what make it a product rather than a demo.

● Q17.2 — Designing a multi-provider abstraction (avoiding vendor lock-in)

Core: Same principle as Dependency Injection in Q8.6 — define a shared protocol, each provider (OpenAI/Anthropic/Apple Foundation Models) is one implementation, and the choice of which provider to use lives in the backend/remote config, never leaking into the domain/UI layer.

protocol AIProvider {
    func streamResponse(to prompt: String) -> AsyncThrowingStream<String, Error>
}

final class OpenAIProvider: AIProvider { ... }
final class ClaudeProvider: AIProvider { ... }
final class AppleFoundationModelProvider: AIProvider { ... }  // uses LanguageModelSession internally

// The ViewModel only knows the protocol — swapping providers = changing 1 line at the composition root
let vm = ChatViewModel(ai: remoteConfig.preferOnDevice ? AppleFoundationModelProvider() : OpenAIProvider())

Go deeper

Why abstract over providers at all — isn't one enough?

Because the thing you're insulating against isn't hypothetical: price changes, rate limits, deprecated model versions, regional availability, an outage during your launch week, and a better model shipping next quarter. An abstraction turns each of those from a refactor into a config change.

It also enables the hybrid you probably want anyway — on-device for cheap tasks, cloud for hard ones — behind one call site.

What belongs in the abstraction, and what must stay out?

In: a message/role model, streaming as an AsyncSequence, tool definitions, a normalized error type, cancellation, and token/usage reporting. Out: provider-specific parameters and vendor quirks — leaking those defeats the purpose. Where a capability genuinely differs, expose it as a declared capability the caller can query, not as an optional field everyone must know about.

What's the hardest part in practice?

Normalizing what isn't actually the same: streaming chunk formats, tool-calling shapes, token accounting, and above all error semantics — one provider's rate limit is another's 500, retryable in one case and not the other. Getting errors into one typed enum with retry guidance is most of the value and most of the work.

How do you avoid the lowest-common-denominator trap?

Design the interface around your product's needs rather than the intersection of every API, and model capabilities explicitly (supports tools, supports vision, max context) so callers can adapt rather than being levelled down. Then keep one provider as the reference implementation and test the others against the same behavioural suite — the abstraction is only real if you can swap it in a test.

Why can't you just send the whole document to the model?

Because of the context window, and because cost and latency scale with input. Even where a long window exists, quality degrades in the middle of very long inputs and you pay for every token on every request. So the design question is not “which model has the biggest window” but how you reduce the document before generation.

Why is map-reduce the standard shape, and where does it fall down?

Map-reduce (summarise chunks, then summarise the summaries) parallelises well, fits any window, and bounds cost. It falls down on documents with cross-references and global structure — a contract where clause 14 modifies clause 3 — because no single chunk sees both. Mitigations: overlap, a hierarchical pass, or a retrieval step to pull related sections into the same chunk.

Why does extraction quality dominate everything downstream?

Because a PDF is not text. A two-column layout linearised wrong, a table flattened into a word salad, a scanned page with no OCR — the model then summarises nonsense fluently, which is worse than failing. The unglamorous parsing work is where summarizer quality is actually won, and saying that signals real experience.

How do you make the output trustworthy for the user?

Ground it: cite the page or section for each claim so the user can verify, show what was skipped (an unparsed page, a truncated section), and never present an inferred number without its source. Then evaluate on a fixed set of documents with known answers so a prompt or model change can be compared rather than vibed. Trust comes from verifiability, not from tone.

● Q17.4 — Controlling cost & latency: cache, token budget, TTFT
  • TTFT (Time To First Token): measured separately from total completion time — streaming keeps TTFT low even when total time is unchanged, improving perceived performance.
  • Token budget: trim history, summarize old conversation instead of sending it verbatim — fewer tokens = lower latency and lower cost.
  • Selective caching: cache deterministic responses (FAQ) by prompt-hash + TTL; don't cache personalized responses or fast-changing data.
  • Model routing: use a small/cheap model for simple tasks (classification), a large model only when deep reasoning is needed.

Go deeper

Why is TTFT the metric to optimise rather than total response time?

Because it's what the user experiences as “is this thing working?”. Perceived responsiveness is set in the first half second; total duration matters far less once text is moving. That's why streaming plus a fast first token beats a faster total that arrives all at once — and why you measure TTFT separately in production.

Which cost levers actually move the bill, in order?

1) Send fewer tokens — trim history, summarise the middle, stop resending static context. 2) Route by difficulty — a small/cheap model for classification, titles and extraction; the strong model only where it shows. 3) Cache — exact-match first, then semantic. 4) Cap output length. 5) Do it on-device where quality allows, which is the only lever that takes cost to zero.

Why is caching harder for LLM responses than for HTTP?

Because the key isn't obvious: prompts are rarely byte-identical, and near-identical prompts may need different answers. Exact-match caching is safe but hits rarely; semantic caching hits more but can serve a subtly wrong answer. And personalised or time-sensitive answers must not be shared across users at all — a cache keyed carelessly is a data-leak bug, not just a correctness one.

What would you instrument from day one?

TTFT and total latency per model, input/output tokens per request, cost per active user, cache hit rate, error and timeout rate by provider, and cancellation rate (high cancels means answers are too slow or too long). Without those, cost regressions are invisible until billing, and “the AI feels slow” stays an anecdote instead of a number you can fix.
