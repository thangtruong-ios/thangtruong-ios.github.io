1. Serial vs Concurrent Queue

● Serial queue và concurrent queue khác nhau ở đâu?

Cốt lõi: cả hai đều là DispatchQueue, khác ở số task chạy cùng lúc.

// SERIAL — 1 task tại một thời điểm, đúng thứ tự FIFO
let serial = DispatchQueue(label: "com.app.serial")   // default = serial
serial.async { print("1") }
serial.async { print("2") }
serial.async { print("3") }
// Luôn in: 1, 2, 3

// CONCURRENT — nhiều task song song trên nhiều thread
let concurrent = DispatchQueue(label: "com.app.concurrent", attributes: .concurrent)
concurrent.async { print("1") }
concurrent.async { print("2") }
concurrent.async { print("3") }
// Thứ tự in: không xác định

Ví dụ có sẵnDispatchQueue.mainDispatchQueue.global(qos:)

Bẫy hay hỏi

1. sync/async là trục khác. sync/async nói về caller có bị block không; serial/concurrent nói về queue chạy bao nhiêu task cùng lúc. Hai trục độc lập.

2. Deadlock kinh điển:

// Đang ở main thread:
DispatchQueue.main.sync { }   // 💥 Deadlock

Main là serial queue đang chạy task hiện tại; sync đợi task mới xong → khóa chết. Tương tự khi sync vào chính serial queue đang chạy.

3. Thread explosion. Đẩy hàng trăm task blocking vào concurrent queue → GCD tạo quá nhiều thread. Giải pháp: DispatchSemaphore giới hạn, OperationQueue.maxConcurrentOperationCount, hoặc Swift Concurrency (cooperative pool giới hạn theo số core).

4. Readers–writer pattern — ứng dụng đẹp nhất của concurrent queue:

final class Cache {
    private var store: [String: Data] = [:]
    private let queue = DispatchQueue(label: "cache", attributes: .concurrent)

    func value(for key: String) -> Data? {
        queue.sync { store[key] }                      // đọc song song
    }
    func set(_ data: Data, for key: String) {
        queue.async(flags: .barrier) { self.store[key] = data }  // ghi độc quyền
    }
}

.barrier khiến task ghi đợi mọi task đọc xong, và block task mới cho tới khi ghi hoàn tất.

Tương đương trong Swift Concurrency

actor ≈ serial queue (tuần tự hóa truy cập state) · TaskGroup ≈ concurrent queue (fan-out song song, có structured cancellation).

2. Task, TaskGroup & async let

● Task { } và TaskGroup khác nhau như thế nào?

Lưu ý syntax: không có TaskGroup { }. TaskGroup là struct bạn chỉ nhận được bên trong closure của withTaskGroup / withThrowingTaskGroup.

Khác biệt cốt lõi: Task { } là unstructured concurrency, task group là structured.

Ví dụ đời thường

Task { } — nhờ một bạn đi mua cà phê rồi quay lại làm việc ngay, không đứng chờ. Muốn bảo bạn ấy dừng thì phải tự nhớ số điện thoại mà gọi lại.

TaskGroup — bạn là trưởng nhóm, chia 10 tấm ảnh cho 10 người rồi đứng chờ đủ 10 người quay lại. Vì đang đứng chờ nên bạn kiểm soát được cả nhóm: bạn hủy thì cả 10 dừng, một người lỗi thì 9 người kia dừng luôn.

// ── Task: không chờ ──
let task = Task { try await fetchUser() }
// code ở đây chạy NGAY
let user = try await task.value      // đợi khi nào bạn muốn

// ── TaskGroup: bắt buộc chờ ──
let total = await withTaskGroup(of: Int.self) { group in
    for url in urls { group.addTask { await download(url) } }
    var sum = 0
    for await size in group { sum += size }
    return sum
}
// tới đây: MỌI child task chắc chắn đã xong

Dùng gì khi nào

Task { } — bắc cầu từ sync sang async, hoặc fire-and-forget:

Button("Load") {
    Task { await viewModel.load() }      // từ sync context vào async
}

// UIKit — phải tự dọn
loadTask = Task { await refresh() }
deinit { loadTask?.cancel() }

TaskGroup — N việc song song cùng loại, cần tất cả kết quả:

func loadThumbnails(_ ids: [String]) async throws -> [String: UIImage] {
    try await withThrowingTaskGroup(of: (String, UIImage).self) { group in
        for id in ids {
            group.addTask { (id, try await fetchThumbnail(id)) }
        }
        return try await group.reduce(into: [:]) { $0[$1.0] = $1.1 }
    }
}

Điểm hay bị hỏi thêm

async let — cũng structured, nhưng cho số task cố định biết trước. Dùng async let khi có 2–3 việc khác kiểu; dùng TaskGroup khi N việc cùng kiểu, số lượng động.

async let user = fetchUser()
async let posts = fetchPosts()
let profile = Profile(user: try await user, posts: try await posts)

Task { } vs Task.detached { }: Task { } kế thừa actor isolation, priority, task-locals; detached không kế thừa gì. detached gần như luôn là sai lựa chọn.

Giới hạn song song trong TaskGroup — group không tự throttle, thêm 10.000 task là 10.000 task:

await withTaskGroup(of: Void.self) { group in
    var iterator = urls.makeIterator()
    for _ in 0..<5 {                                // mồi 5 task đầu
        guard let url = iterator.next() else { break }
        group.addTask { await process(url) }
    }
    while await group.next() != nil {               // mỗi task xong nạp thêm 1
        guard let url = iterator.next() else { continue }
        group.addTask { await process(url) }
    }
}

Cancellation là cooperative. Cả hai loại chỉ đánh dấu cancelled; code phải tự kiểm tra try Task.checkCancellation() hoặc Task.isCancelled, nếu không task vẫn chạy tới hết.

Nói trong interview

"Task là để chạy một việc bất đồng bộ mà không cần chờ — em hay dùng khi cần gọi code async từ chỗ không phải async, ví dụ khi người dùng bấm nút trong SwiftUI.

TaskGroup là khi có nhiều việc cùng loại muốn chạy song song và cần đợi hết mới đi tiếp — ví dụ tải 20 ảnh thumbnail rồi mới hiển thị. Nó chờ tự động, và nếu một việc lỗi thì các việc còn lại được dừng luôn, không chạy vô ích.

Nói ngắn gọn: Task là việc lẻ và tự do; TaskGroup là nhóm việc có người quản lý."

3. Continuation — bắc cầu callback sang async

● Continuation là gì và giải quyết vấn đề gì?

Vấn đề: code cũ dùng callback, không biết await là gì. Continuation là công cụ bọc hàm cũ thành hàm async.

Ví dụ đời thường: gọi điện đặt bánh, cửa hàng nói "chờ chút, xong tôi gọi lại" rồi cúp máy — đó là callback. Continuation là khi bạn nói "tôi cứ giữ máy, xong anh nói vào máy là được": bạn tạm dừng ở đó, và "tờ giấy hẹn" để cửa hàng gọi lại chính là continuation.

// Hàm cũ, dùng callback
func layUserCu(id: String, completion: @escaping (User) -> Void) { ... }

// Bọc lại thành async
func layUser(id: String) async -> User {
    await withCheckedContinuation { continuation in
        layUserCu(id: id) { user in
            continuation.resume(returning: user)     // "xong rồi, đây là kết quả"
        }
    }
}

Hai luật tuyệt đối

Phải gọi resume — đúng một lần.

  • Không gọi → hàm treo mãi mãi, await không bao giờ trả về. Người dùng thấy loading xoay vô tận.
  • Gọi 2 lần → app crash.
// ❌ SAI — nếu error != nil thì không ai gọi resume
layUserCu(id: id) { user, error in
    if let user = user {
        continuation.resume(returning: user)
    }
    // quên trường hợp lỗi → treo vĩnh viễn
}

checked vs unsafe: withCheckedContinuation tự kiểm tra hai lỗi trên và báo cho bạn. withUnsafeContinuation không kiểm tra — nhanh hơn vài chục nanosecond, nhưng sai thì rất khó tìm. Luôn dùng checked.

Lưu ý để không nhầm

Continuation không thuộc riêng về Task — nó là hàm độc lập (withCheckedContinuation), dùng ở bất cứ đâu trong code async.

Nếu callback được gọi nhiều lần (ví dụ vị trí cập nhật liên tục), continuation là sai công cụ vì nó chỉ resume được một lần. Trường hợp đó dùng AsyncStream.

● withCheckedThrowingContinuation — tại sao phải dùng, không dùng có được không?

Bốn biến thể, khác nhau ở 2 trục:

Không lỗiCó thể lỗi
Có kiểm trawithCheckedContinuationwithCheckedThrowingContinuation
Không kiểm trawithUnsafeContinuationwithUnsafeThrowingContinuation

Khác biệt duy nhất của bản throwing: nó cho phép gọi resume(throwing:).

func taiDuLieu() async throws -> Data {
    try await withCheckedThrowingContinuation { c in
        taiDuLieuCu { data, error in
            if let error { c.resume(throwing: error) }
            else if let data { c.resume(returning: data) }
            else { c.resume(throwing: MyError.unknown) }
        }
    }
}

Không dùng thì sao? Ba đường, cả ba tệ hơn

  • Trả optional, ném lỗi đi. Người dùng thấy nil nhưng bạn không biết vì sao — mất mạng? sai token? server sập? Không hiện được thông báo tử tế, không debug được.
  • Trả Result. Giữ được lỗi, nhưng mọi nơi gọi phải tự switch, lỗi không tự lan lên hàm cha, không dùng được do/catch chung.
  • Crash khi lỗi (data!). App chết vì mất wifi.

Lý do thật: nhiều lời gọi dùng chung một chỗ bắt lỗi.

do {
    let user = try await layUser()
    let anh  = try await taiAnh(user.avatarURL)
    let ban  = try await layDanhSachBan(user.id)
    hienThi(user, anh, ban)
} catch {
    hienThiLoi(error)     // một chỗ xử lý cho cả ba
}

Với Result bạn phải switch ba lần lồng nhau.

Cách nhớ tên hàm

Đọc thành ba phần, mỗi phần một câu hỏi: Checked → "muốn Swift kiểm tra hộ không?" → Có · Throwing → "việc này có thể thất bại không?" → Nếu có thì chọn bản này · Continuation → "tờ giấy hẹn để gọi lại".

Thực tế ~90% trường hợp bạn dùng đúng một cái: withCheckedThrowingContinuation.

4. Lan truyền lỗi tới ViewModel

● Có async throws thì ViewModel chỉ cần try/catch là biết lỗi cụ thể?

Phần tự lan lên thì đúng hoàn toàn — các tầng giữa chỉ cần try:

// Tầng network
func taiUser() async throws -> User {
    try await withCheckedThrowingContinuation { ... }
}

// Tầng repository — chỉ try, không catch
func layUser() async throws -> User {
    let user = try await api.taiUser()
    luuCache(user)
    return user
}

// ViewModel — bắt ở đây
func load() async {
    do { self.user = try await repo.layUser() }
    catch { self.loi = error }       // lỗi từ tầng sâu nhất đi thẳng tới đây
}

Ba tầng, một chỗ catch. Đó là giá trị lớn nhất.

Chỗ dễ hiểu sai

Trong catch { }, biến error có kiểu chung là Error. Bạn có đúng object lỗi, nhưng Swift chưa biết nó là loại gì — phải hỏi lại:

catch let error as APIError {
    switch error {
    case .unauthorized:      dangXuat()
    case .notFound:          hienThi("Không tìm thấy")
    case .server(let code):  hienThi("Lỗi server \(code)")
    }
} catch let error as URLError where error.code == .notConnectedToInternet {
    hienThi("Vui lòng kiểm tra kết nối mạng")
} catch {
    hienThi("Có lỗi xảy ra")       // bắt phần còn lại
}

Nên câu trả lời chính xác: try/catch giúp lỗi tới được ViewModel nguyên vẹn; muốn biết cụ thể thì cần kiểm tra kiểu của nó.

Cái bẫy thật sự: lỗi bị "bóp" giữa đường

// ❌ Chặn lỗi, đổi thành nil
func layUser() async -> User? {
    do { return try await api.taiUser() }
    catch { return nil }              // ViewModel chỉ thấy nil, không biết vì sao
}

// ❌ Bọc lại thành lỗi chung chung
catch { throw AppError.somethingWrong }   // mất hết chi tiết gốc

// ✅ Đổi loại lỗi nhưng giữ lỗi gốc
enum AppError: Error {
    case network(underlying: Error)
    case unauthorized
}
catch let error as URLError { throw AppError.network(underlying: error) }

Nói trong interview

"async throws giúp lỗi tự lan từ tầng network lên ViewModel mà các tầng giữa chỉ cần try, không phải viết catch lặp lại.

Nhưng trong catch thì error có kiểu chung là Error, nên nếu muốn xử lý riêng từng loại — 401 thì đăng xuất, mất mạng thì hiện nút thử lại — em phải catch let error as APIError rồi switch trên đó.

Điều em chú ý là không bắt lỗi ở tầng giữa rồi trả về nil, vì như vậy ViewModel mất hết thông tin. Nếu cần đổi loại lỗi thì em bọc kèm lỗi gốc bên trong."

Điểm cộng nếu người phỏng vấn đi sâu

Từ Swift 6 có typed throws — viết async throws(APIError) thì trong catch compiler biết luôn kiểu, không cần cast. Nhưng nó chỉ hợp cho hàm tầng thấp có tập lỗi rõ ràng; lên tầng cao thì lỗi từ nhiều nguồn nên Error chung vẫn tiện hơn.

5. Session expire & đặt observer ở đâu

● post(.sessionDidExpire) ở tầng token — đặt observer ở đâu để logout toàn app?

Nguyên tắc: đúng một người lắng nghe, sống suốt đời app. Sai lầm phổ biến nhất là đặt observer ở nhiều ViewController/View → token hết hạn, 5 màn hình cùng nghe → 5 lần logout, màn hình nhảy loạn.

SwiftUI

@MainActor
final class AppState: ObservableObject {
    @Published var daDangNhap = false

    init() {
        NotificationCenter.default.addObserver(
            forName: .sessionDidExpire, object: nil, queue: .main   // ⚠️ queue: .main
        ) { [weak self] _ in
            self?.dangXuat()
        }
    }

    func dangXuat() {
        guard daDangNhap else { return }     // ⚠️ chống gọi nhiều lần
        KeychainStore.xoaToken()
        daDangNhap = false
    }
}

@main
struct MyApp: App {
    @StateObject private var appState = AppState()      // sống suốt đời app
    var body: some Scene {
        WindowGroup {
            Group {
                if appState.daDangNhap { HomeView() } else { LoginView() }
            }
            .environmentObject(appState)
        }
    }
}

Đổi daDangNhap = false là toàn app tự quay về LoginView — không cần dismiss từng màn hình.

UIKit — đặt ở AppDelegate / AppCoordinator

observer = NotificationCenter.default.addObserver(
    forName: .sessionDidExpire, object: nil, queue: .main
) { [weak self] _ in self?.veManHinhLogin() }

private func veManHinhLogin() {
    guard let window = UIApplication.shared.windows.first else { return }
    guard !(window.rootViewController is LoginViewController) else { return }  // đã ở đó rồi
    window.rootViewController = LoginViewController()
    UIView.transition(with: window, duration: 0.3,
                      options: .transitionCrossDissolve, animations: nil)
}

Bốn lưu ý dễ mắc lỗi

  1. Notification chạy trên thread nào gọi post. post từ tầng network → observer chạy trên background → cập nhật UI ở đó là crash hoặc lỗi lạ. Khai báo queue: .main (gọn hơn tự DispatchQueue.main.async).
  2. Nhiều request cùng nhận 401. 5 API song song → 5 lần post → logout 5 lần. Cái guard daDangNhap else { return } chính là để chặn việc này.
  3. Giữ token của observer (bản block-based trả về một object). Không lưu thì vẫn chạy nhưng không remove được.
  4. [weak self] — thành thói quen tốt, dù AppState sống mãi cũng không sao.

Có nên dùng NotificationCenter không?

Nó hoạt động tốt cho ca này, nhưng nhược điểm là ẩn: đọc code không biết ai đang nghe, tên notification chỉ là chuỗi nên gõ sai không báo lỗi, và test khó.

Cách gọn hơn — SessionManager tự công bố trạng thái bằng @Published, tầng network gọi trực tiếp await SessionManager.shared.hetHan() thay vì post. Rõ ràng hơn, compiler kiểm tra được, dễ test, và @MainActor lo luôn chuyện thread.

Nói trong interview

"Em đặt observer ở một chỗ duy nhất sống suốt đời app — SwiftUI là AppState khai báo @StateObject ở App, UIKit là AppDelegate hoặc AppCoordinator. Không đặt ở ViewController vì nhiều màn hình cùng nghe sẽ logout nhiều lần.

Hai thứ em luôn để ý: dùng queue: .main vì notification được post từ tầng network chạy trên background; và có cờ kiểm tra để nhiều request cùng nhận 401 thì logout chỉ chạy một lần.

Thực tế em thấy dùng một SessionManager với @Published còn rõ hơn NotificationCenter, vì compiler kiểm tra được và dễ test hơn."

6. Singleton — khi nào dùng

● Singleton nên dùng khi nào?

 
final class SessionManager {
    static let shared = SessionManager()
    private init() { }      // ⚠️ bắt buộc — chặn người khác tạo bản thứ hai
}

Nên dùng khi thỏa CẢ HAI

  1. Tồn tại nhiều bản là vô nghĩa hoặc gây sai. Trạng thái đăng nhập (2 phiên cùng lúc là bug), cache ảnh (2 cache thì tốn gấp đôi và không đồng bộ), kết nối database (nhiều kết nối gây tranh chấp file).
  2. Nó đại diện cho một tài nguyên duy nhất thật sự. Chỉ có một cái điện thoại → một UIApplication, một UserDefaults, một FileManager.default. Apple dùng singleton ở đúng những chỗ này.

Không nên dùng

Đừng dùng chỉ vì "cho tiện lấy ở mọi nơi" — đó là lý do phổ biến nhất và cũng sai nhất. Tiện lúc viết, khổ lúc sửa.

APIClient.shared        // ⚠️ nên inject, để test được
UserViewModel.shared    // ❌ ViewModel gắn với màn hình, không dùng chung
Coordinator.shared      // ❌ điều hướng phụ thuộc ngữ cảnh

Ba vấn đề singleton gây ra:

  • Rất khó test. APIClient.shared.get("/user") là gắn cứng — không có cách nào sạch để test mà không gọi mạng thật.
  • Phụ thuộc bị che giấu. Đọc init tưởng class không cần gì; thực ra bên trong gọi 6 singleton khác.
  • Trạng thái dùng chung, thay đổi khó lường. Bất cứ chỗ nào cũng sửa được → có bug không biết ai đã sửa.

Cách "vừa đủ" — singleton nhưng vẫn test được

final class UserRepository {
    private let api: APIClientProtocol
    init(api: APIClientProtocol = APIClient.shared) {   // mặc định tiện, test thay được
        self.api = api
    }
}

let repo = UserRepository()                      // code thật
let repo = UserRepository(api: FakeAPIClient())  // test

Hai lưu ý kỹ thuật

static let đã an toàn về thread khi khởi tạo — Swift đảm bảo chạy đúng một lần. Không cần viết code khóa cho phần khởi tạo.

Nhưng bên trong thì không tự an toàn. Vì singleton được truy cập từ mọi nơi, nó gần như chắc chắn bị gọi từ nhiều thread:

actor ImageCache {
    static let shared = ImageCache()
    private var store: [URL: UIImage] = [:]      // ✅ actor tự tuần tự hóa

    func image(for url: URL) -> UIImage? { store[url] }
    func set(_ image: UIImage, for url: URL) { store[url] = image }
}

Nói trong interview

"Em dùng singleton khi việc có nhiều bản là vô nghĩa hoặc gây sai — trạng thái đăng nhập, cache ảnh, kết nối database. Những thứ đại diện cho một tài nguyên duy nhất thật sự.

Em tránh dùng chỉ vì tiện lấy ở mọi nơi. Vấn đề lớn nhất là khó test: nếu code gọi thẳng APIClient.shared thì em không thể đưa fake vào để test mà không gọi mạng thật.

Cách em dung hòa là vẫn có shared nhưng để nó làm giá trị mặc định của init — code thật gọi init() cho tiện, test thì truyền fake vào.

Về thread thì static let đã an toàn khi khởi tạo, nhưng dữ liệu bên trong không tự an toàn — nên em thường khai báo nó là actor hoặc @MainActor."

Câu hỏi bẫy: "Singleton có phải anti-pattern không?"

"Em không nghĩ nó là anti-pattern, mà là công cụ dễ bị lạm dụng. Apple dùng nó ở UserDefaults.standard, FileManager.default, URLSession.shared — đều hợp lý. Vấn đề là khi người ta dùng nó thay cho dependency injection ở mọi nơi."

protocol Storage {

}

final class DiskStorage: Storage {
    func save(_ data: Data, key: String) throws { try data.write(to: fileURL(key)) }
}

final class KeychainStorage: Storage {
    func save(_ data: Data, key: String) throws {
        guard data.count < 4096 else {
            fatalError("Keychain không lưu được dữ liệu lớn")   // 💥
        }
    }
}

Rồi ở file khác, do người khác viết vài tháng sau:

Tại sao lại có người làm vậy? Không phải vì họ dốt:

  • Người mới vào team — thấy cần một Storage, nghĩ "cache token thì lưu Keychain an toàn hơn". Hợp lý theo góc nhìn của họ, vì protocol không nói gì về giới hạn kích thước.
  • Refactor sau này — ban đầu CacheManager chỉ lưu token (nhỏ) → Keychain đúng. Sáu tháng sau thêm cache avatar vào cùng class.
  • Đổi theo môi trường — isSecureMode ? KeychainStorage() : DiskStorage(). Trông rất "đúng chuẩn", nhưng bật isSecureMode là crash.

Chữa cháy SAI (nhiều người làm):

func luuAnh(_ data: Data) throws {
    if storage is KeychainStorage {           // ⚠️ trừu tượng đã thất bại
        throw CacheError.khongHoTro
    }
    try storage.save(data, key: "avatar")
}

Giờ CacheManager phải biết tên các implementation cụ thể — lợi ích của protocol biến mất.

Tại sao chúng cảm thấy giống nhau — bạn có lý do

Vi phạm I thường dẫn tới vi phạm L. Protocol quá to buộc người ta viết hàm rỗng (I); mà hàm rỗng nghĩa là lời hứa bị phá (L) — ai truyền InternalErrorLogger vào hàm cần logPurchase thì doanh thu không được ghi, im lặng, không ai biết.

Sửa I thường sửa luôn L. Nhưng L còn xảy ra ở chỗ khác — như BaseViewController quên super, ở đó protocol chẳng liên quan gì.

"Em hiểu I là về kích thước của protocol — nếu protocol quá to, class chỉ cần một hàm vẫn phải viết cả chục hàm rỗng.

L là về implementation có giữ đúng lời hứa hay không. Ví dụ protocol Storage, một implementation là Keychain lại fatalError khi dữ liệu lớn — nghĩa là nó không thay thế được cho Storage. Dấu hiệu em nhận ra là khi phải viết if storage is KeychainStorage để kiểm tra trước khi dùng.

Hai cái liên quan nhau ở chỗ: protocol quá to (vi phạm I) khiến người ta viết hàm rỗng, mà hàm rỗng chính là phá lời hứa (vi phạm L). Nhưng L còn xảy ra khi kế thừa class nữa — như override viewDidLoad rồi quên gọi super, cái đó không liên quan gì tới protocol."

// ── Hai nguồn dữ liệu ──
protocol ProductAPIProtocol   { func fetchProducts() async throws -> [Product] }
protocol ProductStoreProtocol { func load() throws -> [Product]
                                func save(_ products: [Product]) throws }

// ── Repository: che đi việc "dữ liệu từ đâu" ──
protocol ProductRepositoryProtocol {
    func products(forceRefresh: Bool) async throws -> [Product]
}

final class ProductRepository: ProductRepositoryProtocol {
    private let api: ProductAPIProtocol
    private let store: ProductStoreProtocol

    func products(forceRefresh: Bool) async throws -> [Product] {
        if !forceRefresh, let cached = try? store.load(), !cached.isEmpty {
            return cached
        }
        do {
            let fresh = try await api.fetchProducts()
            try? store.save(fresh)
            return fresh
        } catch {
            // Mất mạng → dùng cache nếu có
            if let cached = try? store.load(), !cached.isEmpty { return cached }
            throw error
        }
    }
}

Đây là giá trị của Repository: toàn bộ quyết định "lấy cache hay gọi mạng, mạng lỗi thì làm gì" nằm gọn một chỗ.

@MainActor
final class ProductListViewModel: ObservableObject {
    @Published private(set) var products: [Product] = []
    @Published private(set) var isLoading = false

10. Repository chia thế nào

● Repository có phải chứa tất cả func của một feature?

Không. Repository chia theo loại dữ liệu, không theo feature.

  • Feature = một luồng người dùng (Checkout, Onboarding, Profile)
  • Repository = một loại dữ liệu (Product, Cart, User, Order)

Quan hệ giữa chúng là nhiều–nhiều, không phải một–một.

Feature Checkout ─┬─► CartRepository
                  ├─► UserRepository
                  └─► OrderRepository

Feature Cart ─────┬─► CartRepository       ◄── dùng lại
                  └─► ProductRepository

Feature Profile ──┬─► UserRepository       ◄── dùng lại
                  └─► OrderRepository      ◄── dùng lại

UserRepository được 5 feature dùng. Nếu chia theo feature, CheckoutRepository và ProfileRepository sẽ cùng gọi API user — code trùng, cache trùng, sửa một chỗ quên chỗ kia.

● Logic phức tạp đến mức nào thì nên tách Use Case?

Không phải "logic phức tạp" chung chung. Có bốn dấu hiệu cụ thể:

1. Một hành động cần nhiều repository — khi ViewModel phải phối hợp nhiều nguồn dữ liệu theo một trình tự, đó là business logic.

func datHang() async {
    isLoading = true
    defer { isLoading = false }
    do {
        // ───── BƯỚC 1: Lấy giỏ hàng và user ─────
        async let cartTask = cartRepo.currentCart()
        async let userTask = userRepo.currentUser()
        let (cart, user) = try await (cartTask, userTask)

        // ───── BƯỚC 2: Kiểm tra điều kiện nghiệp vụ ─────
        guard !cart.items.isEmpty else { errorMessage = "Giỏ hàng đang trống"; return }
        let hetHang = cart.items.filter { !$0.isAvailable }
        guard hetHang.isEmpty else { errorMessage = "\(hetHang[0].name) đã hết hàng"; return }
        let subtotal = cart.items.reduce(0) { $0 + $1.price * Double($1.quantity) }
        guard subtotal >= 50_000 else { errorMessage = "Đơn tối thiểu 50.000đ"; return }

        // ───── BƯỚC 3: Lấy địa chỉ giao hàng ─────
        guard let address = try await addressRepo.defaultAddress() else {
            errorMessage = "Vui lòng thêm địa chỉ giao hàng"; return
        }
        guard address.isDeliverable else {
            errorMessage = "Chúng tôi chưa giao tới khu vực này"; return
        }

        // ───── BƯỚC 4: Xử lý voucher ─────
        var voucher: Voucher?
        if !voucherCode.isEmpty {
            voucher = try await promoRepo.voucher(code: voucherCode)
            guard let v = voucher, v.isValid(at: .now) else {
                errorMessage = "Mã giảm giá không hợp lệ hoặc đã hết hạn"; return
            }
            guard subtotal >= v.minimumOrder else {
                errorMessage = "Đơn tối thiểu \(v.minimumOrder)đ để dùng mã này"; return
            }
        }

        // ───── BƯỚC 5: Tính giá ─────
        let memberDiscount = user.isVIP ? subtotal * 0.1 : 0
        var voucherDiscount: Double = 0
        if memberDiscount == 0, let v = voucher { voucherDiscount = v.amount(for: subtotal) }
        let totalDiscount = min(memberDiscount + voucherDiscount, subtotal * 0.5)
        let shippingFee = address.isRemoteArea ? 50_000.0
                        : (subtotal >= 500_000 ? 0 : 30_000)
        let total = subtotal - totalDiscount + shippingFee

        // ───── BƯỚC 6: Đặt hàng và dọn dẹp ─────
        let order = try await orderRepo.place(cart: cart, total: total,
                                              address: address, voucher: voucher)
        try await cartRepo.clear()
        if let v = voucher { try await promoRepo.markUsed(v.code) }

        navigateToSuccess(order)      // ← rốt cuộc mới tới việc của ViewModel
    } catch {
        errorMessage = "Đặt hàng thất bại, vui lòng thử lại"
    }
}

● PlaceOrderUseCase — implement đầy đủ

Bước chuẩn bị: lỗi nghiệp vụ mang theo DỮ LIỆU, không phải câu chữ

enum OrderError: Error, Equatable {
    case gioHangTrong
    case hetHang(tenSanPham: String)
    case duoiDonToiThieu(toiThieu: Double)
    case chuaCoDiaChi
    case khongGiaoTiKhuVuc(tenKhuVuc: String)
    case voucherKhongTonTai
    case voucherHetHan(ngayHetHan: Date)
    case voucherChuaDuDieuKien(donToiThieu: Double)
}

Nhờ vậy đổi từ ngữ hiển thị không cần chạm Use Case, và làm đa ngôn ngữ cũng dễ.

Implementation

protocol PlaceOrderUseCaseProtocol {
    func execute(voucherCode: String?) async throws -> Order
}

struct PlaceOrderUseCase: PlaceOrderUseCaseProtocol {
    let cartRepo: CartRepositoryProtocol
    let userRepo: UserRepositoryProtocol
    let addressRepo: AddressRepositoryProtocol
    let promoRepo: PromotionRepositoryProtocol
    let orderRepo: OrderRepositoryProtocol
    let calculatePrice: CalculatePriceUseCase

    func execute(voucherCode: String?) async throws -> Order {

        // ═══ BƯỚC 1: Thu thập dữ liệu — 3 lời gọi độc lập, chạy song song ═══
        async let cartTask = cartRepo.currentCart()
        async let userTask = userRepo.currentUser()
        async let addressTask = addressRepo.defaultAddress()
        let (cart, user, addressOrNil) = try await (cartTask, userTask, addressTask)

        // ═══ BƯỚC 2: Kiểm tra giỏ hàng ═══
        guard !cart.items.isEmpty else { throw OrderError.gioHangTrong }
        if let hetHang = cart.items.first(where: { !$0.isAvailable }) {
            throw OrderError.hetHang(tenSanPham: hetHang.name)
        }
        let subtotal = cart.items.reduce(0) { $0 + $1.price * Double($1.quantity) }
        guard subtotal >= Constants.donToiThieu else {
            throw OrderError.duoiDonToiThieu(toiThieu: Constants.donToiThieu)
        }

        // ═══ BƯỚC 3: Kiểm tra địa chỉ ═══
        // Phải trước bước 5 vì phí ship phụ thuộc địa chỉ
        guard let address = addressOrNil else { throw OrderError.chuaCoDiaChi }
        guard address.isDeliverable else {
            throw OrderError.khongGiaoTiKhuVuc(tenKhuVuc: address.district)
        }

        // ═══ BƯỚC 4: Xác thực voucher ═══
        let voucher = try await validateVoucher(voucherCode, subtotal: subtotal)

        // ═══ BƯỚC 5: Tính giá — giao cho use case chuyên tính giá ═══
        let price = calculatePrice.execute(cart: cart, user: user,
                                           voucher: voucher, address: address)

        // ═══ BƯỚC 6: Đặt hàng, RỒI MỚI dọn dẹp ═══
        // Thứ tự bắt buộc: place() phải thành công trước clear() —
        // nếu clear trước mà place lỗi thì khách mất giỏ hàng.
        let order = try await orderRepo.place(cart: cart, price: price,
                                              address: address, voucher: voucher)

        // Dọn dẹp — KHÔNG được làm hỏng kết quả đặt hàng thành công
        try? await cartRepo.clear()
        if let voucher { try? await promoRepo.markUsed(voucher.code) }

        return order
    }

    private func validateVoucher(_ code: String?, subtotal: Double) async throws -> Voucher? {
        guard let code, !code.isEmpty else { return nil }
        guard let voucher = try await promoRepo.voucher(code: code) else {
            throw OrderError.voucherKhongTonTai
        }
        guard voucher.expiresAt > .now else {
            throw OrderError.voucherHetHan(ngayHetHan: voucher.expiresAt)
        }
        guard subtotal >= voucher.minimumOrder else {
            throw OrderError.voucherChuaDuDieuKien(donToiThieu: voucher.minimumOrder)
        }
        return voucher
    }
}

CalculatePriceUseCase — hàm thuần

struct PriceBreakdown: Equatable {
    let subtotal: Double
    let memberDiscount: Double
    let voucherDiscount: Double
    let shippingFee: Double
    var total: Double { subtotal - memberDiscount - voucherDiscount + shippingFee }
}

struct CalculatePriceUseCase {
    func execute(cart: Cart, user: User, voucher: Voucher?,
                 address: Address) -> PriceBreakdown {
        let subtotal = cart.items.reduce(0) { $0 + $1.price * Double($1.quantity) }

        // Quy tắc: VIP giảm 10%
        let memberDiscount = user.isVIP ? subtotal * 0.1 : 0

        // Quy tắc: voucher không cộng dồn với giảm giá thành viên
        var voucherDiscount: Double = 0
        if memberDiscount == 0, let voucher, voucher.isValid(at: .now) {
            voucherDiscount = voucher.amount(for: subtotal)
        }

        // Quy tắc: tổng giảm không vượt 50% giá trị đơn
        let maxDiscount = subtotal * 0.5
        let totalDiscount = min(memberDiscount + voucherDiscount, maxDiscount)
        let raw = memberDiscount + voucherDiscount
        let scale = raw > 0 ? totalDiscount / raw : 0

        // Quy tắc: trên 500k miễn phí ship, trừ vùng xa
        let shippingFee: Double = address.isRemoteArea ? 50_000
                                : (subtotal >= 500_000 ? 0 : 30_000)

        return PriceBreakdown(subtotal: subtotal,
                              memberDiscount: memberDiscount * scale,
                              voucherDiscount: voucherDiscount * scale,
                              shippingFee: shippingFee)
    }
}

● Mỗi Use Case chỉ có một execute — vậy ViewModel phải giữ 5 Use Case?

Ba phép thử để tự quyết định

  1. "PO/business có bao giờ yêu cầu đổi cái này không?" — "Đổi mật khẩu tối thiểu lên 10 ký tự" → có → Use Case. "Đổi từ AES sang RSA" → PO không nói câu này → Data layer.
  2. "Bên Android có làm giống y hệt về mặt logic không?" — Quy tắc mật khẩu: giống y hệt → Domain. Mã hóa: cùng thuật toán nhưng dùng thư viện khác của Android, code hoàn toàn khác → Data layer. Domain là cùng logic; mã hóa là cùng kết quả nhưng cách làm khác nhau tùy nền tảng.
  3. "File này có phải import thư viện kỹ thuật không?" — Use Case phải import CryptoKit, import Compression → gần như chắc chắn nó đang giữ việc không thuộc mình.

Ngoại lệ: khi mã hóa LÀ nghiệp vụ

App password manager, hoặc chat có end-to-end encryption — lúc đó "cái gì được mã hóa, khóa của ai, ai giải mã được" là chính sản phẩm. Nhưng cách tổ chức vẫn tương tự: Use Case giữ quyết định, service giữ thuật toán.

protocol CryptoService {                                    // infra
    func encrypt(_ data: Data, with key: PublicKey) throws -> Data
}

struct SendSecureMessageUseCase {                            // domain
    let crypto: CryptoService
    let keyRepo: KeyRepositoryProtocol
    let messageRepo: MessageSending

    func execute(_ text: String, to recipientID: String) async throws {
        // Quyết định NGHIỆP VỤ: mã hóa bằng khóa công khai của người nhận
        guard let key = try await keyRepo.publicKey(of: recipientID) else {
            throw ChatError.chuaCoKhoaCongKhai
        }
        // Nhưng KHÔNG tự viết thuật toán
        let encrypted = try crypto.encrypt(Data(text.utf8), with: key)
        try await messageRepo.send(encrypted, to: recipientID)
    }
}

Use Case này nói "phải mã hóa bằng khóa của người nhận" — nghiệp vụ. Nó không nói "dùng Curve25519" — việc của CryptoService.

  • File này phải import thư viện kỹ thuật gì? → Nếu Use Case phải import là sai tầng
  • API team đổi endpoint X thì tôi sửa mấy file? → Nhiều file là chia sai
  • Copy file này sang project command-line có compile được không? → Được thì Use Case sạch

Điều rút ra chung của cả buổi: phần lớn quyết định thiết kế ở đây đều nhằm biến một bug lúc chạy thành một lỗi lúc compile, hoặc biến bốn chỗ phải sửa thành một chỗ. Nếu một cách tách không làm được điều nào trong hai điều đó, có thể nó chưa cần thiết.
